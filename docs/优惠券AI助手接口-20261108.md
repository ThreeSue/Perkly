# 优惠券 AI 助手

最新任务续接与拦截处理见[优惠券AI任务续接与拦截处理-20261109.md](优惠券AI任务续接与拦截处理-20261109.md)。`clarification.type`新增`REPAIR`、`CREATE`、`MERCHANT`；`/confirm`可返回`data.recovery`，表示原确认失败且已回滚，需展示新的Reply并等待再次确认，不能提示执行成功。原成功响应保持兼容。

模块收尾版本的能力边界和实际运行证据见[优惠券AI模块收尾验收-20261109.md](优惠券AI模块收尾验收-20261109.md)。旧轮次结果不代表本版完整验收。

## 扩展编辑与原表单交接

`Fields`增加：`maxDiscount`（折扣券最高优惠，元）、`allowCombine`（0/1）、`validityType`（FIXED/AFTER_ISSUE）、`validFrom/validTo`、`saleStartTime/saleEndTime`、`scopeType`（0全部营业门店/1指定）、`storeNames`（完整门店名称数组）。日期为明确的北京时间`yyyy-MM-ddTHH:mm:ss`；只有日期但没有时刻时追问，不默认为全天。

- 固定日期和领券后天数互斥，切换时预览说明旧方式被清除；同一预览支持多字段修改和修改后送审。
- 指定门店仅按目标券所属商家的营业门店精确匹配；同名、跨商家、停用或未授权范围不能通过预览/执行。使用展示名称，不让模型构造数据库ID。
- `contentItems`支持完整清单替换，复用原内容与商品关联服务。仅说“加一道菜”但没有完整清单时须补充或进入原表单，不能猜测其余项目。未明确修改的字段不变。
- `EDIT_FORM`和`EDIT_COVER`返回`detail`及`operation=编辑表单/编辑封面`，不返回执行令牌、不写数据库。前端按钮转到原有编辑表单；封面继续用已有CoverField、AI图片任务及素材库，保存仍走原业务接口。图片模型、额度、素材授权不另建。
- 清空日期/优惠上限、修改券型等使用原表单；不以null表达隐式清空。发放渠道创建后不能切换。
- 自然语言解析增加`QuerySpec.clearEvidence=[{field,quote}]`。移除筛选须引用本条用户原文，不能把助手对占比分母的说明当成清除指令。客户端不构造此内部字段，仍只发送文本、历史和服务端令牌。
- 有查询上下文但没有目标券时，疑似写操作先区分“改筛选”还是“改券”。解析和回复各最多两次调用，最终失败返回503；不能声称业务已完成。

`/chat`仍使用既有请求和回复字段。普通修改、库存及审核确认继续使用`/confirm`，确认时重新检查权限、版本、关联和事务结果。确认端点返回的执行状态是后端事实；模型润色不能替代该状态。

单券删除按真实业务规则规划。草稿或停用券在未发放、没有发布历史、商品内容、发放批次或用户券关联时直接预览删除。启用券满足同样条件且账号同时具有修改与删除权限时，预览“先禁用，再删除”，一次确认后在同一事务中执行。已有历史关联即使撤回审核或下架仍不能删除。确认时重新锁定并核对快照和关联，任一步失败回滚。禁用后删除成功会反馈“我已经帮你禁用了这张券，随后也把它删掉了。”直接删除只反馈删除结果。

统一管理端的“AI 工作台”和优惠券管理页的“AI 助手”共用优惠券助手。运营使用 `/admin/ai/assistant/coupon`，商家使用 `/merchant/governance/ai/assistant/coupon`。会话由页面保留，助手的右侧对话和草稿核对区互斥显示。

| 接口 | 请求 | 返回 |
| --- | --- | --- |
| POST `/chat` | text，history（最多16条 role/text），可选 merchantId、storeId、couponId、selectedIds、answer、planToken、queryToken | text，choices，draft，changes，token，可选 clarification、queryToken、countResult |
| POST `/confirm` | token | 操作结果。修改并送审成功时，data.message 包含券名和待审核状态 |
| POST `/detail` | couponId，可选 merchantId、storeId | 可访问的优惠券详情 |

服务端使用现有百炼文本模型配置做结构化意图解析。统计查询固定在后端执行，按登录账号权限收窄商家和门店范围。查券结果会列出实际采用的筛选条件。遇到多个修改候选时，按下文的澄清接口继续。助手使用文本模型理解需求，图片生成沿用优惠券封面的既有模型、额度、任务记录与素材入库接口。

优惠券款数按模板分类统计，包含草稿、启用与停用。已支付销量按成功支付的订单及明细购买数量求和，以支付时间归档。购券订单没有成交门店归属，选择门店时须清除门店筛选才能查询销量。核销按成功核销记录计数，以实际核销门店及核销时间统计。未给出日期时查询近30个北京时间自然日，最长366天。

新建先返回草稿，在表单中补全门店及券内容，保存通过现有新增接口。草稿使用现有表单的发券后30天、每人限领1张默认值，核对后可修改。启用与送审继续使用原优惠券管理流程。

修改当前支持券名、使用说明、售价、最低消费及与券类型相符的优惠金额。删除展示目标及业务限制。确认令牌与操作人、身份、目标快照绑定，有效期10分钟。执行时重新校验权限和快照，通过原有业务服务修改或删除。

## 库存澄清与修改后送审

问候、身份和使用方式由对话路径回答。业务正文（含款数及查询汇总）基于服务端核实的结果，由模型组织措辞，并参考最近六条对话自然承接、变化表达。校验失败时最多重新生成一次；模型不可用或再次校验失败时提示重试，不再回显后端统计原文。模型正文与真实卡片分别处理。

预览后继续说「改成80」时携带原 `planToken`，服务端撤销原令牌再生成新预览。单一数值可直接改口；多字段预览可继续新增、纠正或撤销某一字段，例如「售价保持原来的，折扣保留」，未提及的改动保留。送审步骤独立保留、增加或取消，仍须核对新预览后确认。「先别改」撤销当前账号助手的待办与确认令牌。预览中的输入框可直接改口或取消。候选选择阶段说「就这张」时，服务端核对当前唯一选择确实属于此前候选。

普通修改字段共用同一套澄清协议。券名、使用说明、售价、最低消费、抵扣金额、减免金额、折扣、领券后有效天数和每人限领缺少新值时，助手按字段逐项追问，保留已明确的值和送审要求。例如说「售价改成29元，再改一下折扣，改完送审」，回答「8 折」即可看到两项修改和送审的预览。金额、折扣和天数仍按模板现有规则校验。

- 在列表只勾选一张券后，说「把这个券的库存调整到50，并提交审核」。助手先问剩余可领数量还是发行总量。点选「剩余可领数量」，或回复「我是说剩下能领的数量」，都会保留 50 和送审要求。多选时先确定目标。直接说「把这张券的剩余可领设为50张并提交审核」可以进入预览。
- `clarification` 含 `token`、`type`、`question`、`options`。`type` 取 `CANDIDATE`、`SINGLE`、`NUMBER` 或 `TEXT`。候选来自响应的 `choices`，单选值来自 `options`。按钮用 `answer: { token, value }`，候选 ID 作为字符串传入；直接聊天只传 `answer: { token }`，答案放在 `text`。每次续答保留原商家、门店及选中券上下文。澄清令牌有效期10分钟，成功续答后作废，重新发起请求会替换当前澄清。
- 发行总量必须大于零，且不低于已发放数量。剩余可领数量换算为已发放数量加目标剩余数量。预览同时列出发行总量、剩余可领及审核状态，确认前不写入。
- 已启用、可送审的券可以一次确认。服务端锁定目标，重新检查修改与送审权限、门店范围和券快照，保存后使用新规则版本送审。库存已经是指定值时，预览会说明将直接送审当前版本。任一步失败都会回滚。快照变化时须重新预览。

## 2026-11-09 查询与统计上下文

免费指模板售价 `salePrice = 0`，付费指 `salePrice > 0`，不是库存或领取记录。模板保存规则将未填售价归零，数据库字段非空且默认0；查询不把异常空值猜成免费。支持组合名称、券型、模板状态、审核状态、上架状态、商家、门店、免费/付费和售价上下界（包含/不包含边界）。仍然逐次应用账号与门店数据范围。

`queryToken` 是服务端返回的不透明查询范围令牌，与账号、身份及页面选择范围绑定，有效期30分钟，不授予额外权限。前端在当前聊天中单独保存最新令牌，后续请求原样携带；换商家、门店或选中券时清除。错误回复没有新令牌时保留原查询令牌以便纠正条件。不能从显示文字拼接令牌，也不能在账号之间复用。

解析器输出受控查询增量：新查询重置、追问继承；明确新增或纠正的条件覆盖旧值，明确取消的条件从范围移除。空的可选售价对象不等于清除售价条件。统计范围保存在服务端，而不是只凭前端历史文字恢复。过期、伪造或范围不一致的继承请求会被拒绝并要求重新说明范围。

款数统计返回 `countResult`：

```json
{
  "matched": 2,
  "baseTotal": 4,
  "percentage": 50.00,
  "priceCondition": "免费领取（售价为0元）",
  "scope": "示例商家（授权门店范围）、代金券、已上架",
  "groups": [{ "label": "代金券", "count": 2 }]
}
```

此为格式示例，不是线上统计。`matched` 是符合全部条件的模板款数；`baseTotal` 保留同一授权、商家、门店、名称、类型及状态，仅移除售价条件。`percentage` 为 `matched / baseTotal * 100`，四舍五入到两位小数；分母为0时为 `null`。可按券型、免费/付费、模板状态分组。模型根据本轮问题决定回答重点与句式，正文中的统计数字使用受控事实占位符，由程序替换成对应真实值；不允许新增数字或未知占位符。只问总数时不必展示分母和100%，问占比时才解释相应范围。措辞可变化，但不保证每次必然不同。

同一目标与日期范围内同时请求销量、核销时，`operation` 为「查询汇总」，后端分别执行查询，模型根据已核实的各项结果组织回复；无权限或业务限制的项目单独说明未完成，已成功的项目保留。汇总仅支持款数、单券销量、单券核销三项，不支持任意工具组合或跨步骤不同时间基准。

「最近N天」由模型提取整数天数，由后端计算北京时间含今天的N个自然日（1至366天），不让模型自行做日期减法。绝对日期仍采用含首尾的起止日期。模板款数不支持日期快照，混合汇总中不能执行的日期款数部分会单独说明。

目前不支持模板款数的历史日期快照、周末可用等规则筛选、任意分组、同比/环比和自定义占比分母。识别到无法映射的条件时会列出缺项并询问是否去掉条件，不执行宽泛统计冒充完整答案。模型仍可能误解自然语言，不能将此机制视为任意问题都可回答。

管理端详情在聊天正文中展示，不替换整个聊天视图。接口失败原因加入聊天记录供后续理解；切换目标会清除旧确认卡与查询令牌。后端写操作仍走原有权限、快照和确认接口。
