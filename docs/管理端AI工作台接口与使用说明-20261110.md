# 管理端 AI 工作台接口与使用说明

适用运营、商家与门店管理后台。移动端 AI 客服是另一套接口，不要混用本契约。

## 入口与能力

顶部“AI 工作台”、左侧固定“AI 助手”进入全局对话；已接入业务页面顶部操作/筛选行最右侧的 AI 图标打开或收起窄侧栏，图标短暂轻动效提示入口，开启减少动态效果时保持静止。优惠券沿用专用助手，并使用同款图标入口。

| 模块 | 能力 |
|---|---|
| 优惠券 | 复用原助手查询、草稿、修改核对及业务操作；全局支持与分类/类型组合任务，券任务独立核对确认 |
| 商家分类、门店类型 | 查询、新增、编辑、删除预览，确认时重新验证权限、引用、目标变化；仅运营原权限开放 |
| 商家、门店 | 原授权范围查询；运营支持全量数量和启用状态分布 |
| 购券订单、消费账单 | 只读查询，消费账单金额字段单位为分；购券价格按原接口单位 |
| 核销 | 运营按时间及商家/门店统计成功次数、前20条记录；商家授权列表；门店复用独立报表的本人/授权范围 |
| 员工、岗位、授权 | 复用原账号、岗位、授权管理服务查询；岗位权限附名称，不提供任何修改工具 |
| 审批、活动 | 原权限范围只读；审批查看遵循原页面的查看权限或审核权限 |
| 通知 | 本人收发、未读数量、本人已发回执；查询不标记已读或确认。写作仅生成候选稿，采用后回填，仍需用户选择收件人和发送 |

并非全库任意查询。字段和数据范围按工具目录限制；不支持的统计不能推断。资金、退款、结算、人员/权限、活动写入不在本轮范围。

## 接口

基础路径：运营 `/admin/ai/assistant/workbench`；商家/门店 `/merchant/governance/ai/assistant/workbench`。沿用对应身份的 `Authorization`，标准响应 `{code,message,data}`。

2026-11-10 数据一致性修订：`pageContext` 是可选页面路径，目前识别 `/approval/coupon` 与 `/approval/merchant`，用于明确优惠券发布审核和商家入驻审核；它不是权限凭据，未知路径不进入模型上下文。旧客户端可不传。

审批查询支持 `type`、`status`、`publishStatus`、关键词。审批状态为 0 已撤回/未提交、1 待审核、2 已通过、3 已驳回；券上架状态为 0 未上架、1 已上架、2 已下架，不能将审核通过当成已上架。商家入驻审核不接受上架状态。

审批 READ 的 data 返回 `{type,status,publishStatus,keyword,total,page,meaning}`。`total` 是全部筛选条件下的数据库总数，`page.list` 只包含前 20 条；AI 不能将列表长度当成总数。页面和助手复用同一审批服务。用户提出数量异议时应重新查询，不应猜测权限、缓存或同步原因。

| 方法 | 后缀 | 请求/响应 |
|---|---|---|
| GET | `/capabilities` | 返回 `[{module,read,actions}]`；按钮能力按当前登录者，不代表可绕过执行时校验 |
| POST | `/chat` | `{sessionId?,requestId,scope,text,selectedId?,pageContext?}` → Reply |
| POST | `/confirm` | `{sessionId,token}` → Reply；仅确认当前分类/类型预览；优惠券使用原券接口独立确认 |
| POST | `/cancel` | `{sessionId}`；取消本会话未执行待办，不撤销已完成步骤 |
| POST | `/notice-draft` | `{instruction,title?,content?,previous?:{title,content}}` → `{title,content}`；需原通知发送权限，但本接口不发送 |

`scope`：GLOBAL、COUPON、CATEGORY、STORE_TYPE、MERCHANT、STORE、ORDER、CONSUMPTION、REDEMPTION、STAFF、APPROVAL、ACTIVITY、NOTICE。侧栏指定自身 scope，跨模块返回 `handoffText`，前端明确点击后转工作台。

`requestId` 为8～64位字母、数字、下划线或连字符，推荐UUID。相同请求标识和相同消息/选中目标重放返回已保留结果，换文本或目标必须换标识。`text` 最多1500字。

Reply：`{sessionId,text,results,preview,degraded,handoffText}`。

- `results[]`：`{module,state,note,data}`；READ 为真实查询，PREVIEW 未写入，COMPLETED 才完成，FAILED 保留失败原因，DRAFT 为通知候选稿。
- `COUPON_RESULT.data`：`{text,reply}`，reply 是原优惠券助手 Reply。前端直接接续该真实结果，不重复请求模型、不自动确认。
- `preview`：`{token,steps}`。仅点击确认执行后写入；执行时重新核验当前数据。部分步骤成功后再次确认只继续未完成步骤。
- `degraded=true`：模型文案暂不可用；保留真实卡片，不把文字失败误判为业务回滚。
- 会话绑定账号、身份、登录令牌与 scope，空闲30分钟失效；分类/类型预览有效期30分钟。切账号不可复用原会话。会话存在当前后端进程内，多实例需粘性路由；重启后重新发起会话，不承诺跨重启续聊。

## 手工验收例句

1. “查询商家分类。”随后“给这个分类改个排序，先预览。”——缺值追问，不能猜值保存。
2. “新增门店类型‘开发验收体验店’，排序20，启用，先预览。”随后“排序改30。”——旧预览失效，新预览确认后落库。
3. “查询今天成功核销次数，不统计收入。”——仅原授权范围，不编造收入、利润或失败次数。
4. “查询待审核的优惠券，不审批。”——只读，不调用审核写接口。
5. “查询员工岗位以及岗位权限，不修改。”——通过原角色查询展示权限名称。
6. “帮我起草系统维护通知，时间还没确定，不发送。”——时间占位，采用回填，收件人仍由用户选择。
7. 在通知侧栏发“查询门店类型。”——不越界查询，显示前往工作台入口。

验收使用隔离数据库 `perkly_ai_regression_20261106` 的临时数据，不把测试夹具令牌、模型密钥提交仓库。
