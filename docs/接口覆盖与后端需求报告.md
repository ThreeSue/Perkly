# 券管家 3.0 接口覆盖与后端需求报告

更新日期：2026-10-21  
用途：供后端组员评估、确认并补充接口契约。  
范围依据：根目录 `券管家3.0_数据库表规划(1).md`；已知接口还包括 `docs/BACKEND-DISCOVERY-API-20261020.md` 中记录的客户端门店与优惠券查询接口，以及用户提供的 `用户端购券券包与商家核销接口.md`。

## 1. 结论摘要

当前已同步普通用户与管理员账号接口、顾客端行业分类/门店/优惠券只读查询契约，以及用户购券、免费领券、模拟支付、订单、顾客券包和商家核销契约。客户端已接入浏览、购券/免费领券、订单、券包及二维码调用代码，待真实账号联调；用户明确本轮只做用户接口，三个商家核销接口继续暂缓。商家核销主流程已有契约，但员工登录、授权门店查询等支撑能力，以及券管理/发布审核、经营统计等其他商家功能仍有接口缺口。

数据库规划是逻辑数据模型，不是 API 契约。下文未确认的功能仍按“需要后端提供的接口能力”描述，不预设 URL、HTTP 方法、请求字段或响应结构；已确认的顾客端展示接口以 `BACKEND-DISCOVERY-API-20261020.md` 为准。

### 2.5 用户购券、券包与商家核销（用户端已接入代码，商家本期暂缓）

2026-10-21 开工更新：用户明确本轮只做用户接口。客户端领购、订单、券包、持券详情及鉴权PNG备用读取已按契约接入代码；三个商家核销接口暂缓，相关适配尝试已撤回。尚未完成真实账号/双端联调，详见 [客户端接入记录](./CLIENT-TRADE-INTEGRATION-20261021.md)。下表是接口能力映射，不能作为实联调完成证明。

接口定义见用户提供的 `用户端购券券包与商家核销接口.md`。下表只确认接口文档支持的产品能力，不表示前端页面或真实服务联调已完成。
跨端实施阶段、前置依赖和验收场景见 [客户端与商家端购券核销闭环计划](./客户端与商家端购券核销闭环计划-20261021.md)。

| 使用端 | 接口能力 | 可以新增的用户功能 | 关键限制 |
|---|---|---|---|
| 客户端 | `POST /app/order/claim`、`POST /app/order/create`、`POST /app/order/simulatePay`、`POST /app/order/cancel` | 在现有优惠券详情增加免费领取或付费购券；选择每单 1–20 张；免费券领取后立即发券；付费券创建待支付订单、查看 15 分钟有效期并执行模拟支付或取消 | 不接微信支付/真实资金；模拟支付结果以服务端响应为准；下单不预占库存，支付时会再次检查库存和限购；无购物车，一单一种券 |
| 客户端 | `POST /app/order/page`、`GET /app/order/info` | 我的订单列表与详情；按待支付、已完成、已取消、支付失败、已超时查看订单状态 | 列表是摘要，详情才包含明细；只能查询当前登录用户自己的订单 |
| 客户端 | `POST /app/coupon/wallet/page`、`GET /app/coupon/wallet/info`、`GET /app/coupon/wallet/qrcode` | “我的券”接入真实券包，按待使用/已使用/已过期/未生效/已作废筛选；查看有效期、适用门店、发券时的规则快照、完整券码及后端生成的二维码 | 列表不含券码；详情可直接显示后端提供的 PNG/Base64，不要求前端自行生成二维码；券码和二维码属于用户私有数据 |
| 商家端 `apps/merchant` | `POST /merchant/redemption/preview`、`POST /merchant/redemption/confirm` | 扫码或手动录入券码，提交门店与必要的实际消费金额；先展示后端预检结果和优惠/权益，再由商家明确确认核销 | 预检不锁定资格；确认时服务端重新检查券状态、有效期、门店范围等；同券只能核销一次；套餐/体验/兑换券允许不填消费金额 |
| 商家端 `apps/merchant` | `POST /merchant/redemption/page` | 查看本商家核销流水，可选按门店筛选，显示券名、门店、操作员、消费金额、优惠金额和核销时间 | 只查本商家；接口没有按操作员筛选或汇总统计，也不返回顾客手机号和券码 |

#### 新增闭环

1. 客户端沿用现有公开优惠券详情取得模板 ID。免费券调用 `claim`；付费券先 `create`，再由客户端调用 `simulatePay`，成功后发券。客户端可通过订单详情的 `couponIds` 或券包查询展示发券结果。
2. 用户打开券包详情展示后端生成的二维码。商家端扫码或手输完整券码后调用 `preview`，向店员展示券、门店、消费金额和核算出的优惠/权益；确认后调用 `confirm`，成功结果才代表核销完成。
3. 用户券包的状态由服务端核销结果动态反映；商家通过核销流水查询确认经营侧记录。客户端接口未提供顾客核销历史查询，不能据此新增个人消费明细页。

#### 仍需契约或产品确认的功能

- 商家端本轮已有的登录页和“授权门店”入口仍需员工/商家会话能力及当前账号可操作门店查询；本接口要求使用商家 Token，并说明现阶段沿用已启用的 `OWNER` 商家账号，没有给出店员登录或门店列表接口。不能让前端硬编码 `storeId`、伪造店员身份，或把用户 Token/管理员 Token 当商家 Token。
- 商家端的店长/店员权限区分、店员个人核销记录、按操作员统计、营业数据/销售统计没有由这三个接口覆盖。流水只支持本商家全量或按 `storeId` 筛选。
- 商家查券、快速建券、提交审核和审核状态查询仍需各自的商家券管理/发布接口；本次商家核销接口不能替代建券或平台审核。
- 客户端“消费记录”没有独立顾客核销记录接口。订单可展示购券状态，券包可展示已使用状态及 `usedAt`，但不能将其包装成含完整消费详情的历史流水。
- 付费购券在产品上应明确标注为演示用模拟支付，不应显示为微信支付、支付成功即代表真实收款或支持退款。失败结果不发券；库存、限购、过期和规则版本变化均可能使支付失败。

## 3. 五个应用的接口覆盖情况

| 应用 | 目前有资料的接口 | 主要缺口 |
|---|---|---|
| 客户端 `apps/client` | 普通用户账号；公开行业分类、门店分页/详情、优惠券分页/详情已接入代码；购券、订单、券包、二维码已有契约 | 接入本次购券与券包接口并完成真实服务/小程序地址联调；商品/活动浏览、消费明细、内容消息等仍缺接口 |
| 商家端 `apps/merchant` | 核销预检、核销确认、商家核销流水已有契约 | 前端接入核销接口；员工/商家登录与门店授权、店员权限、经营统计、券模板管理、发布申请/审核、活动等仍缺契约 |
| 平台管理端 `apps/platform-admin` | 管理员登录/资料/退出；商家行业分类 CRUD | 商家入驻审核、券/活动发布审核、平台内容、反馈处理、管理记录及所需查询 |
| 商家核销端 `apps/verification` | 商家核销接口契约已提供，但本项目已确认的本次商家手机核销流程归属 `apps/merchant` | 不因接口可复用而合并或迁移应用职责；若要在独立核销端使用，需按其独立登录/发布边界另行接入与验收 |
| 商家独立端 `apps/merchant-independent` | 当前接口文档未列独立品牌业务接口 | 品牌配置读取、商家范围隔离，以及其顾客端需要的浏览/领券/购券/券包能力；账号映射方式需后端确认 |

## 4. 请后端提供的接口能力

以下按数据库规划中的阶段和业务分组。具体路径、方法、字段由后端根据现有代码确定后提供，不在本报告里臆造。本次新增文档已经明确购券、订单、券包、二维码和商家核销的路径与 DTO；这些行标注为契约已交付、前端待接入，不再作为后端接口缺口重复提出。

### 4.1 第一阶段：核心闭环接口状态

数据库规划建议先建立 17 张表，目标流程为“账号权限 → 建券 → 平台审核 → 模拟购券 → 券包 → 核销”。下表标出已有契约和剩余缺口；具体实现仍按已确认的接口契约进行：

| 模块 | 需要的接口能力 | 主要使用端 | 依据与边界 |
|---|---|---|---|
| 员工账号与权限 | 员工登录、当前账号/角色/权限查询、商家归属和可操作门店范围查询；必要的退出或会话失效处理 | 商家、平台管理、核销 | 对应 `sys_user`、角色/权限关联和 `sys_user_store`；现有管理员登录是否能复用，需后端确认 |
| 顾客账号 | 将现有普通用户账号与 3.0 `customer` 身份关联；查询/维护顾客资料 | 客户端、商家独立端 | 现有账号接口已覆盖部分能力，但需确认是否对应规划中的 `customer`，两个顾客端是否共用身份 |
| 券模板管理 | 商家创建、查询、编辑券模板及规则；第一阶段管理适用门店关系。商品关联待商品模块阶段再对齐 | 商家 | 第一阶段对应 `coupon_template`、`coupon_store`；`coupon_product` 属于后续商品关联能力，不列入首批 17 张表 |
| 券渠道发布与审核 | 按渠道提交发布内容；查看审核/上架状态；平台审核通过或驳回并记录原因；发布/下架及审核历史查询 | 商家、平台管理 | 对应 `coupon_publication`、`audit_record`；平台客户端与商家自有端的发布状态独立 |
| 顾客可用券查询 | 查询当前渠道可展示的券及详情、适用范围和使用规则 | 客户端、商家独立端 | 平台审核通过且已上架的券展示契约已提供；领券/购买契约见 2.5，商家独立端适用渠道仍需确认 |
| 顾客领券 | 顾客领取当前可领取的券；记录来源、渠道和限领结果 | 客户端、商家独立端 | **契约已交付，前端待接入**：`/app/order/claim` 免费券即时发券并以 `requestId` 幂等；批量/定向发券及 `coupon_issue_batch` 仍属后续能力 |
| 模拟购券订单 | 创建购券订单、查询订单列表/详情/状态，并按约定记录模拟支付结果和时间 | 客户端、商家、平台管理 | **契约已交付，前端待接入**：包含创建、模拟支付、取消、分页和详情；仅做模拟业务，不接真实支付渠道 |
| 订单发券 | 模拟购券成功后按订单明细数量生成顾客券；可按订单/明细查询发券结果 | 后端业务、客户端读取 | **契约已交付**：成功支付后事务内生成持券、唯一券码和二维码；前端通过订单详情或券包读取，不单独调用发券接口 |
| 顾客券包 | 查询券列表、券详情、券码、有效期、适用门店和当前状态 | 客户端、商家独立端 | **契约已交付，前端待接入**：含券包分页、持券详情和 PNG 二维码；顾客身份从登录态确定，不由客户端传入任意顾客 ID |
| 券核销 | 按券码查询核销预览，校验商家/门店/操作员范围，确认核销并查询成功核销记录 | 商家（apps/merchant） | **契约已交付，前端待接入**：含预检、确认、本商家分页流水；服务端重复检查并保证单券至多成功一次。员工登录、门店授权查询和汇总统计仍需补充 |

| 问题反馈 | 顾客/员工提交反馈，查询处理状态；处理人回复并保留回复历史 | 客户端、商家、平台管理 | `feedback`、`feedback_reply` |
| 商家独立品牌 | 查询对应商家的品牌、主题、首页内容和入口配置；授权商家维护配置 | 商家独立端、商家 | `merchant_client_config`；不得由客户端自行指定或切换 `merchant_id` |
| 审核与操作记录 | 按业务类型/对象查询审核历史；按权限查询管理操作记录 | 平台管理、商家管理 | `audit_record`、`operation_log`；记录写入由服务端业务操作产生 |

### 4.3 扩展模块：单独确认后再排期

| 模块 | 需要的接口能力 | 规划状态 |
|---|---|---|
| 储值与充值 | 查询商家范围余额及流水、查询充值档位、创建/查询模拟充值订单、按已确认规则赠券 | 数据库规划中的扩展模块；余额与流水需后端事务处理 |
| 积分 | 查询积分余额/规则/流水，查询可兑换权益，提交兑换并查询兑换记录 | 数据库规划中的扩展模块；扣积分与发权益需幂等处理 |
| 推广访问统计 | 创建/读取推广入口、记录访问、查询统计 | 仅在确实要展示推广访问量时需要；简单分享链接/二维码本身不一定需要独立表 |
| 独立小程序身份 | 按 provider、app_id、openid 映射顾客身份 | 仅当第五端确认为真正独立小程序且需要跨端身份关联时提供；当前规划明确为条件表 |

## 5. 本期明确不提出的接口

- **购物车接口不在 3.0 数据库规划中，本报告不要求后端提供购物车能力。** 旧客户端购物车演示和旧 API 草案不构成需求。
- **真实微信支付接口不在当前规划中。** 订单采用数据库规划中的模拟购券/模拟支付，不接第三方支付，不预建退款、提现、结算或发票接口。
- 不因存在数据库表就要求为每张表提供通用 CRUD。审核记录、核销流水、余额/积分流水等应由对应业务动作产生，并仅在界面确有查询需求时提供读取能力。
- 不从数据库字段自行推导接口路径、请求字段或状态枚举；具体协议由后端确认。

## 6. 请后端在接口文档中一并确认

1. 每个接口的路径、方法、请求/响应 DTO、分页格式、错误码和状态枚举。
2. 顾客、平台员工、商家员工和核销员的认证方式、角色权限、商家隔离及门店数据范围。
3. 现有普通用户账号如何映射到 3.0 的 `customer`；两个顾客端是否共用顾客身份。
4. 券在不同发布渠道的库存/每人限领规则是否共用；发布审核状态与顾客持券状态分别维护。
5. 体验券是否需要多次核销；当前数据库规划按一次性券设计。
6. 模拟支付允许的状态流转、重复请求结果、失败/取消规则，以及购券后发券时点。
7. 商家独立端是同一应用内的品牌入口还是真正独立小程序；这决定是否启用外部身份映射。
8. 储值和积分是否按商家独立核算；数据库规划目前是建议方案，仍待确认。

## 7. 联调前置条件

- 后端提供可访问的开发环境地址和上述接口契约；小程序/真机环境不能使用设备自身的 `127.0.0.1` 访问开发机。
- 明确测试账号、商家和门店数据、各角色权限，以及模拟购券、发券、核销的可重复验证步骤。
- 前端按五个独立应用分别配置认证与数据权限；不能用管理员分类接口代替顾客端查询，也不能用前端本地状态伪造订单、券或核销结果。
