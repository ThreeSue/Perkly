# 客户端与商家端购券核销闭环功能增加计划

拟定日期：2026-10-21  
状态：用户已授权开工并进一步限定本轮只做用户接口；P1/P2 客户端接入代码已完成，P3/P4 商家部分按用户要求暂缓。真实发券及跨端联调未完成。实施证据见 [客户端接入记录](./CLIENT-TRADE-INTEGRATION-20261021.md)。  
范围：`apps/client` 与 `apps/merchant` 通过同一后端连接“公开券模板 → 用户持券 → 商家核销 → 用户券包状态更新”。不改变五个独立应用和各自登录边界。

## 1. 目标闭环

```text
客户端浏览已上架券
  ├─ 免费券：领取 ───────────────┐
  └─ 付费券：创建订单 → 模拟支付 ─┤
                                  ↓
                         后端生成 customer_coupon
                         唯一券码与 PNG 二维码
                                  ↓
客户端“我的券”查看券码/二维码
                                  ↓
商家端选择授权门店 → 扫码/手输 → 后端预检 → 店员确认
                                  ↓
                         后端原子核销并写流水
                                  ↓
客户端刷新券包后显示“已使用”
商家端刷新核销流水后显示本次记录
```

两端不互相直连、不传递本地券状态，也不共享 Token。客户端只用顾客登录 Token；商家端只用商家 Token。后端的 `customer_coupon`、券码和核销流水是跨端唯一事实来源。

## 2. 计划新增功能

### 客户端 `apps/client`

1. **优惠券详情领取/购买**：免费券调用 `POST /app/order/claim`；付费券调用 `POST /app/order/create`。数量默认为 1，支持 1–20 张。金额只用于展示，不能由客户端提交售价或自行认定支付成功。
2. **模拟支付与订单**：付费券订单创建后显示待支付状态和 15 分钟有效期，提供模拟支付、取消入口；增加我的订单列表/详情，展示待支付、已完成、已取消、支付失败、已超时状态。
3. **真实券包**：将 `pages/index/template.uvue` 的未接入状态页接到 `POST /app/coupon/wallet/page`，按待使用、已使用、已过期、未生效、已作废筛选；增加持券详情，展示发券时的规则快照、有效期、适用门店、券码和后端生成的二维码。
4. **刷新已核销状态**：用户重新进入券包或手动刷新时读取后端状态。当前接口没有顾客核销历史流水，因此不增加完整消费明细页。

### 商家端 `apps/merchant`

1. **商家登录与门店上下文**：取得商家 Token，读取当前账号及可操作门店，明确当前选中门店。接口契约文档说明暂沿用已启用的 `OWNER` 商家账号；前端还需获得现有商家登录和门店列表的正式契约。
2. **扫码/手输预检**：在 `pages/business/verify.uvue` 接入 `POST /merchant/redemption/preview`。小程序使用扫码，H5保留手动输入；扫码结果必须是券码，不把任意二维码 URL 当作可信券码。按券类型收集需要的实际消费金额，使用整数分请求。
3. **明确确认核销**：展示后端预检返回的券名、门店、消费金额、优惠金额或套餐内容；由店员确认后调用 `POST /merchant/redemption/confirm`。仅当确认接口成功才展示核销成功，并显示流水 ID/时间；预检不锁定资格，确认失败需保留可纠正的输入。
4. **核销流水**：在 `pages/business/records.uvue` 接入 `POST /merchant/redemption/page`，分页查看本商家记录，可按门店筛选。当前契约没有操作员、时间、券类型筛选，也没有今日汇总和店员/店长权限规则，不在首轮页面中伪造这些能力。

## 4. 接口与数据约束

- 客户端下单/领券只传 `couponTemplateId`、数量和 `requestId`。同一 `requestId` 只能用于同一模板和数量的重试；更换模板或数量必须生成新的 `requestId`。请求结果不确定时在当前操作上下文复用原 `requestId`，不能为重试创建第二笔订单。
- ID 严格区分：公开模板 ID 用于领取/下单；订单 ID 用于订单接口；`couponIds` 和券包记录 `id` 是持券 ID；商家核销使用二维码内完整券码及所选门店 ID。不能把模板 ID、订单 ID 或持券 ID 当券码。
- `/app/**` 请求携带顾客登录 Token，`/merchant/**` 请求携带商家 Token；用户 ID、商家 ID、操作员 ID 均由后端登录态推导，不由客户端伪造。JSON 响应按 `code == 1000` 判断成功，否则显示后端 `message`；二维码图片接口按二进制/图片响应单独处理。
- 金额接口字段统一为整数分。页面可格式化成人民币显示，但请求时按确定的分值提交；前端不计算最终优惠，展示后端预检返回的计算结果。
- 付费券只调用后端 `simulatePay`；不接微信支付、支付宝或真实收款。不预占库存，模拟支付时可能因库存、限购、过期、下架或规则版本变化失败。
- 后端订单/持券/核销状态不写入本地存储或 mock。页面临时输入和当前操作的幂等 ID 可保留在运行内存；成功结果通过接口重新查询。
- 顾客券包详情快照是已发券权益依据。二维码由后端生成；核销以持券数据库状态为准，前端不能自行标成已使用。
- `/merchant/redemption/preview` 当前响应不含券类型、售价、有效期、完整规则和门槛。如果核销确认页需要展示这些具体字段，应先由后端扩充预检 DTO；否则首轮只展示当前契约给出的券名、门店、消费/优惠金额及套餐内容。

## 5. 联调验收场景

1. 免费券：登录顾客 → 领取 → 券包出现一张新持券 → 打开详情查看二维码。
2. 付费券：创建订单 → 模拟支付成功 → 订单变为已完成并生成指定数量持券；客户端提交期间重复点击或网络重试只产生一个订单/一组持券。
3. 支付失败、库存耗尽、限购超限、超时订单取消/支付：按后端订单状态展示，不出现持券或假成功。
4. 商家用适用门店扫描或手输券码 → 预检返回服务端权益 → 明确确认 → 核销成功并产生唯一流水；另一商家或不适用门店不能核销。
5. 对同一券再次预检/确认、使用过期/未生效/作废券，或在预检后由另一请求先完成核销：确认阶段必须以服务端最新校验拒绝，前端不生成第二条成功记录。
6. 核销后刷新客户端券包，状态显示已使用；刷新商家流水能看到对应门店、时间和优惠数据。客户端不展示商家接口未提供的顾客手机号或个人核销流水。
7. 退出或切换顾客/商家账号后，不残留上个身份的订单、券包、门店和流水；H5 与微信小程序都使用各自可访问的开发服务地址完成验收。

## 6. 首轮不纳入

- 真实支付、退款、购物车、分次核销、券与外部收银系统自动结算。
- 商家建券、发布审核、经营统计、店员个人统计、平台管理流程；需另有契约。
- 客户端顾客消费历史详情接口、券过期/审核/核销主动推送；本次契约未提供。
- `apps/verification` 应用的合并或职责迁移；用户已确认此次手机核销功能归属 `apps/merchant`。
