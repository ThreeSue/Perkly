# 客户端与商家端临时互通测试

日期：2026-10-21。用户要求用临时商品、优惠券数据测试互通，测后删除；随后指定后端工程 `C:\Users\Eric\Perkly`，允许临时测试登录。本次仅做检查和临时测试，没有修改后端业务、补建数据库表或开放前端假登录。

## 结果

**商品、优惠券跨端业务互通尚不能通过验收。** 本地后端实现、数据库和前端商家接入均不完整，不能仅靠假登录解决。

### 本地运行服务

地址为客户端现配置 `http://127.0.0.1:8001`；本机运行进程的命令行指向 Perkly。

| 请求 | 实际结果 |
| --- | --- |
| GET `/app/merchant/category/list` | HTTP 200，code 1000 |
| POST `/app/merchant/store/page` | HTTP 200，code 1000，total 0 |
| POST `/app/coupon/page` | HTTP 200，code 1001，提示“请求方式不正确或服务出现异常” |
| POST `/app/order/page`，无Token | HTTP 401；仅说明鉴权拒绝，不能据此认定业务路由存在 |
| POST `/merchant/redemption/page`，无Token | HTTP 401；同上 |

### 真实数据库与后端测试

执行 Perkly 现有 `AppDiscoveryPersistenceTest`，使用其已有事务回滚机制创建商家、分类、门店和券模板临时记录。10项中4项通过，1项断言失败、5项错误。

通过：门店分页与内部字段保护、商家/门店停用过滤、分页/ID校验、公开路由注册。未通过：券发布可见性、门店适用券、库存状态、商品关联详情、封面关联及游客券列表等，均在券查询或发布记录操作处受到缺表影响。明确异常：`Table 'cool.coupon_publication' doesn't exist`。

随后执行一次性 `TemporaryInteropProbeTest`，直接检查 local 配置的本机 MySQL `cool` 库：

| 表 | 状态 |
| --- | --- |
| coupon_template | 存在 |

| coupon_store、coupon_product、coupon_publication | 不存在 |
| purchase_order、purchase_order_item、customer_coupon、coupon_redemption | 不存在 |

源代码检查也未发现商品模块或购券、券包、商家核销对应 Controller；现有优惠券管理入口是 `/admin/coupon/template/*`，属于运营接口，不能冒充商家身份接口。

### 临时测试登录

一次性测试中生成独立临时顾客，设置随机密码并只在测试进程内使用。通过正式 `POST /app/user/login/password` 获取后端Token，再调用 `GET /app/user/info/person`，登录和本人资料查询均成功；不带Token查询返回401。没有调用短信或微信，也没有保存测试密码/Token到本报告。

此结果验证顾客密码登录与鉴权机制可用，不代表商家登录、发券或核销已经实现。未增加应用运行时的绕过鉴权入口。
