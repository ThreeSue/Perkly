# 五模块业务决策

2026-11-02：用户要求接续开发并授权对未定事项合理决策、记录；后端在前，统一管理网页在后；两个移动端只交文档；修改采用逐行补丁。以下区分用户确认与实施决策，不把旧建议当确认。

## 用户已确认

- 通知：仅向下级、指定具体人员；运营到商家/门店，商家到本商家授权门店，门店管理岗位到本店员工；普通店员不能发送。自定义管理岗和商家成员需上级授予发送权。
- 反馈：平台受理、支持图片、无需多轮回复。
- 聊天：门店全部工作人员可回复，支持图片。
- 储值：现有模拟支付充值，1元=1元余额、无赠送；所有平台正常门店可消费；支持直接消费账单和购券；暂不退款。
- 活动：商家申请须平台审核，商家仅自己的门店；平台可发布；首版为储值支付折扣，力度由运营设定；直接消费与购券均适用，多活动不叠加、取最大优惠。

## 实施决策

1. 通知为站内纯文字，无短信/订阅消息、附件、删除或撤回；每个收件账号独立已读，历史不随成员变化串号。内置店长及有发送权的自定义岗视为管理岗，门店不能通知同级管理岗；未获发送权的自定义普通岗位可被本店管理岗通知。旧内置普通店员即使误配发送权仍不能发。
2. 新目录不自动扩大既有商家上限/岗位/个人权限；通知收件可从顶部进入。门店共享聊天因用户明确全体工作人员均可回复，提供顶部入口，不要求另获管理类权限；服务端仍校验有效岗位、唯一门店绑定及商家状态。
3. 反馈实名登录、正文1至2000字、最多9张图，平台一次文字回复后保留原记录；同内容重试幂等，不做多轮、转派、匿名、删除或关闭重开。
4. 聊天按顾客+门店建立唯一共享会话；所有有效本店工作人员共同处理并显示实际发送人快照，不指定专属客服。3秒轮询、消息ID游标；不做WebSocket、撤回、已读回执和保留期自动清理。正常营业店可发起，临时停业可继续既有沟通；关闭/禁用店不能继续发送，有效顾客仍可读取本人的既有历史，无效岗位不能处理门店消息。
5. 图片复用现有本地文件存储与实际内容校验，增加上传归属记录。只允许引用本人通过客服图片接口上传的URL；JPG/PNG/GIF、5MB、4000万像素、单业务最多9张。不用外部URL或旧上传接口绕过归属。
6. 储值卡按一个顾客一个平台虚拟账户实现，不加实体卡号、转赠、提现、赠额或自动扣过期余额。余额及流水用整数分，拒绝JSON浮点截断；单笔上限100000000分、余额上限1000000000分，作为本期演示边界。充值失败留失败流水、不入账；不提供运营任意修改余额。
7. 直接消费由有redeem:use的门店/商家人员开具无券账单，随机billNo交给付款顾客；顾客先看门店和金额、试算后确认扣款，员工不能代扣。无券账单与原“持券核销消费账单”分开，防止同一核销补款重复收取。支付后不能取消；未支付开单可取消。SELF只看本人账单相关消费。
8. 购券先复用原下单，再由储值支付调用现有库存、限购、规则版本、发券事务，不重写发券。需选择订单商家下原券适用门店以匹配活动，支付活动不改变原券核销范围；免费券仍用原claim。原购券totalAmount保留原价，实扣以储值流水为准。
9. 支付预览不是承诺锁价；确认时须传expectedAmount，服务端重算，不相等返回409且不扣款。顾客/余额行锁、随机账单状态锁、唯一幂等及关联交易索引共同防重复扣款。充值/支付目标或金额改变不能复用已成功请求标识；超时保留原请求原内容。
10. 平台可发全正常门店活动或指定门店；商家申请限自身授权门店且不得自设折扣，活动查询和下架同样核对当前授权范围。审批后发布；开始含、结束不含；不允许编辑已发布记录覆盖历史，下架/驳回后另提新申请。无报名、名额、抽奖或额外关联券专区。
11. 折扣大于0小于10、最多两位小数，9为九折；整数分四舍五入、最低应付1分。只取优惠最大单项，同额优先较新。直接消费按原额折扣、购券按原售价折扣，充值不打折。历史流水保存活动和金额快照，不被后续下架/账号更名重算。
12. 统一网页按现有名称及中文状态显示，ID仅作API关系。商家/门店储值查询不返回顾客个人余额，平台及本人可见。聊天权限不顺带赋予开单/查全店账务权。
