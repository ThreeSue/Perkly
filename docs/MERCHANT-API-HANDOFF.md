### 2026-10-25 入驻后平台审核与结果确认（前端状态结构已恢复，正式契约待交付）

用户确认账号在入驻提交后即可登录商家小程序；平台审核通过前不得上架商品及使用正常经营权限。用户已授权实现首页顶部可展开半页面审核进度，审核完成后弹出结果，点击确定后收起首页提示但保留申请及历史。当前前端适配器明确标记不可用，仅保留界面与状态结构；没有开发测试服务、模拟审核或预置账号，未实现后端或正式接口。本节下方是正式对接需求，不能视作真实平台已经联通。

建议交互：提交申请并取得账号 → 登录受限工作台，顶部显示“资料已提交/等待平台审核” → 平台审核 → 通过时展示结果弹窗，服务端按角色与门店授权开放经营能力 → 点击确定并确认成功后收起进度。驳回时建议保留原因及修改重提入口；进度使用真实业务节点，不生成虚假百分比。后台审核完成时商家若离线，下一次进入首页再展示结果。

后端所需能力（不是确定的新 URL/字段；可组合或扩展已有账号、权限、消息能力）：

| 能力 | 需明确的行为 |
| --- | --- |
| 入驻申请提交与账号创建/绑定 | 同时确定商家、初始店长账号、门店及申请归属，返回可追踪申请；重复提交不重复创建账号/商家。账号可登录，但申请待审不具备经营资格 |
| 商家登录与当前上下文查询 | 返回账号身份、商家归属、角色/门店范围、当前入驻资格和实际可用权限；不能用“账号禁用”表达“入驻待审”而阻断登录 |
| 当前申请与进度/结果查询 | 当前提交版本、状态、提交/审核时间、驳回原因、待确认结果标识及确认状态；登录及首页重新显示时可同步；不信任前端传入的商家归属 |
| 结果确认 | 服务端持久化当前账号对指定审核结果/申请版本的确认，重复确认无副作用；建议按账号+申请版本记录，通知店长还是全部员工需明确。可复用站内消息已读，但必须绑定明确审核结果，不能读错版本 |
| 驳回后修改重提（建议） | 查询本人申请资料并按允许字段修改，生成可追溯的新提交版本；保留历史审核，规定待审能否修改，不覆盖旧版审核依据 |
| 平台审核列表与详情 | 平台管理端查看入驻申请、资料快照、版本、状态及历史，按平台审核员权限访问 |
| 平台通过/驳回 | 对指定申请版本作出审核决定，记录审核员/时间/原因，避免两人同时处理覆盖结果；通过时更新商家经营资格并产生可查询结果，驳回原因可展示给商家 |

状态和权限应独立：已登录不等于入驻已通过；已通过也不等于所有员工拥有全部经营权限。实际操作资格需同时满足账号有效、商家经营可用、角色操作权限及授权门店范围。弹窗“确定”只确认结果，不负责开通经营资格。确认后隐藏首页进度模块，申请详情与审核历史仍可查询。商家入驻通过不自动将商品/券上架，也不替代商品/券既有发布审核。

同步与异常建议：优先登录/首页显示/手动刷新查询，需更及时再增加仅前台低频轮询；一期无须依赖实时推送。状态未知或请求失败不误放行经营；顶部可显示获取失败和重试。弹窗去重到具体审核结果，确认失败可重试且不能写本地“永久已读”冒充成功；返回新审核版本后旧查询/旧确认不可把新进度隐藏。

主要难点在服务端经营权限统一拦截、审核与权限同步、旧 Token 权限更新、并发审核和重提版本隔离、跨登录/设备结果确认。后端应明确允许待审访问的基础功能与拒绝的经营接口，并提供可识别错误响应；前端按钮与路由限制仅用于交互。当前没有开发测试工具，也不模拟审核；前端适配器明确不可用，正式鉴权仍待后端。前端视图模型和 API 适配边界见 apps/merchant/types/merchant-admission.ts、api/merchant-onboarding.ts、stores/merchant-admission.ts，具体请求字段/枚举仍由后端确认映射。完整实施、截图和验收边界见 merchant-admission-20261025/README.md。

### 2026-10-25 一次扫码、按券类型分流（已接入；以下保留接入前方案记录）

用户要求：满减/折扣/代金券识别后弹框填写消费信息，展示优惠和应补差价，收款后确认核销；套餐/体验/兑换券识别后展示内容，员工确认后自动开单并核销。全程沿用首次券码，不重复扫码。以下为接入前方案记录；实际接入见本章收尾状态。

建议流程：已验证商家身份和门店 → 扫码取得完整券码 → 后端识别持券、类型、规则及权益快照 → 按类型展示金额表单或权益明细 → 必要时后端试算 → 员工明确确认 → 后端完成最终校验与提交 → 展示单据/核销结果。类型不可从券名、二维码前缀猜测；未知类型不允许继续核销。页面临时保留当前券码与识别上下文，输入修改后旧试算失效，旧请求响应不可覆盖新输入或新券。

接入前识别的契约缺口（历史记录，实际接口已按新文档接入；以下是能力需求，不是新端点或 DTO）：

- 首次识别：目前 preview 按消费类券需要金额，响应又未包含券类型，不能直接完成“先识别再填金额”。后端需确认扩展 preview 支持无金额识别，或另行提供识别能力；返回券类型及对应输入要求、券状态、门店适用性、规则/权益快照。
- 金额试算：明确消费总额、参与优惠金额（如有不参与优惠项目）、门槛、折扣封顶、金额精度/舍入、代金券不足面额时的处理规则；权威响应应能展示本次抵扣/优惠和应补金额。购券时支付的售价与到店本次应补金额分开，不能再次抵扣售价。字段和规则待后端确认。
- 开单并核销：现有 confirm 仅确认核销，不承诺自动开单。先明确“单”指到店消费/服务履约记录及与购券订单的关系；不能直接复用购券创建/模拟支付来完成开单。建议由后端一个业务提交保证开单、持券状态变更及核销流水一起成功或一起失败，并返回关联单号及核销结果。
- 重试与查结果：后端需提供提交幂等及可追溯的结果查询，首次扫码上下文关联到同一笔提交；双击、并发和超时重试不得重复开单或核销。已有“禁止再次核销”约束不能替代可查询的原提交结果。
- 认证与收款：仍需正式商家会话及逐店员工授权。当前按员工在线下确认到账后点击“已收款，确认核销”理解，不扩展真实微信支付；如需程序自动判断到账，需另行明确支付能力和服务端支付状态契约。权益券如有补差，规则及收款步骤也需补充确认。

前端后续实现可继续复用 verify.uvue、Cool Unix 表单及弹层；金额类与权益类共用一次扫码上下文和提交状态。成功后按后端结果刷新记录及券包；前端不写本地成功状态替代后端。验收至少覆盖六类分流、未达门槛/封顶/不参与优惠、已用/过期/错误门店、金额变更后的重新试算、提交超时查询、并发确认及开单失败不核销。

2026-10-21 用户开工后明确限定：本轮只开发新接口文档的用户部分，三个商家核销接口暂缓。本轮尝试的商家接口适配已撤回，商家端保持原有待接入状态；下文保留接口能力分析，不能视作已经接入。未来商家工作仍需正式登录/会话/授权门店契约。

商家端为独立 Cool Unix / uni-app x 工程，使用既有 cl-page、cl-button、cl-form、cl-form-item、cl-input、cl-textarea、cl-select-date。商家现为黑白灰内容布局与既有中性玻璃导航（早期蓝灰白为历史）；底部悬浮导航：工作台、核销记录、我的。没有安装另一套 UI 或后端框架。

当前 docs/BACKEND-API-20261013.md 只确认顾客账号、平台管理员账号与管理员分类接口，未确认它们可用于商家员工。本轮不调用这些接口替代员工认证，不向商家端注入管理员/顾客 Token。新增接口文档现已提供商家核销预检、确认和本商家核销流水契约；但员工/商家会话和可操作门店查询仍缺，且本次接口文档要求使用商家 Token、现阶段沿用启用的 `OWNER` 账号。因此这三项当前仍未接入前端，不能用硬编码门店或假身份绕过前置条件。其它商家业务接口仍待交付。

后端可以直接在前端工程补接，也可提供契约后由前端开发者接入。统一入口：apps/merchant/api/index.ts；当前 merchantCapabilities 标记缺口，requestMerchantCapability 对缺失能力明确 reject，不返回伪造数据。此入口不是可用的网络实现；接入时需新增真实请求、数据映射及相应页面的加载/失败/重试/空结果/分页状态，不能只把按钮 disabled 去掉。

## 当前可操作和暂不可操作

- 可浏览全部页面；工作台功能跳转、底部导航、券码/查券/记录搜索词临时输入及清空可用。日期可通过Cool滚轮确认或取消，尚未发送请求；记录权限由已验证身份派生，默认未认证，不提供范围切换。
- 登录表单、授权门店、记录查询/搜索/日期筛选请求、建券、审核记录和反馈均待接入；核销预检/确认/基础流水虽然已有契约，但当前因商家会话和门店上下文缺失而未接入，提交保持禁用，不存草稿，不显示成功。券类型/状态/后端权限枚举未确定，不提供虚构选项。
- 二维码扫描暂未启用：未验证员工与门店前不申请相机权限；接口接入后按 H5 / 微信小程序能力接入 uni.scanCode，取消保留手输内容，失败给出文字原因；不自动把二维码 URL 当作可信券码。
- 核销记录明细、券详情和审核详情没有真实记录作为入口，当前保留说明；后续按契约实现详情展示，不能用表结构拼假数据。
- 不开放本地演示登录、不使用 mock、不保存业务数据、不造统计、券码、员工或门店。

## 接入顺序与验收

1. 先交付 M01/M02/M13，建立商家端独立身份、会话过期处理和可操作门店上下文。退出/过期清空私有列表和当前门店，使在途响应失效；不能恢复上个员工的私有数据。
2. 在商家 Token 和已授权门店可用后接 M04/M05：扫码或手输→后端预检→展示返回的权益与试算→店员明确确认→服务端再次校验并核销。按钮请求期间防重复、失败保留可纠正输入；按新契约处理核销流水 ID/时间，不自行标记成功。
3. 接 M06 基础分页流水；M03/M07 的店长/店员统计、按操作员/时间/券类型筛选及记录详情需补契约。异步防过期响应，区分加载/错误/无结果；未授权不拉取数据。
4. 接 M09/M11/M12；建券字段按正式类型规则渲染，失败保留输入；成功收到真实返回后再进入审核列表。反馈不得自行假报提交成功。
5. 后端验收：跨商家/门店隔离、撤销授权、普通店员访问店长接口、过期/作废/已使用券、最低消费门槛、并发重复核销、网络超时重试、版本快照、审核驳回原因。前端不能替代事务/幂等约束。

生产 API 域名、微信 AppID 和独立员工账号/门店授权方案尚未确认；新核销契约规定二维码解码结果应为完整券码，但相机扫描仍需在获得商家身份和门店上下文后接入。前端本次未接新接口，不代表真实员工登录、核销或审核已可用。
