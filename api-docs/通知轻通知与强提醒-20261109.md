# 通知：轻通知与强提醒

更新：2026-11-09。后端与统一管理端增量实现；两个移动端源码未修改。

## 身份、权限与兼容

- 运营使用 `/admin/workspace/notices`，ADMIN token；商家/门店管理端和核销移动端使用 `/merchant/governance/notices`，MERCHANT token，沿用 `Authorization` 与 `X-Workspace`。
- 这是工作人员上下级通知。普通顾客 APP token 仍不可使用；用户移动端无需新增工作人员通知入口。本次未新增顾客营销通知接口。
- 保持原有 `notice:send` 与实时上下级授权：运营选下级，商家选授权门店人员，门店管理岗选本店普通员工；普通店员不能发送。收件和确认不要求发送权限，仍要求有效登录及有效账号、岗位和商家状态。
- 历史通知、类型为 null、旧调用方不传类型均视为 `LIGHT`。活动自动通知保持 `LIGHT`。不会自动把历史通知变成弹窗。
- 成功响应 `{"code":1000,"message":"success","data":...}`；以 code 判断业务结果，认证失败亦可能直接返回HTTP 401/403。下面JSON中的ID、时间、姓名为协议示例。

## 发送

`POST /send`

```json
{"requestId":"notice_20261109_001","title":"营业安排确认","content":"请核对明日安排。","recipientIds":[101,102],"noticeType":"STRONG"}
```

`noticeType` 只能为 `LIGHT`（轻通知）或 `STRONG`（强提醒），大小写敏感，空字符串和其他值返回业务code400。省略或null为LIGHT。
其他校验不变：requestId为8至64位字母数字下划线短横线；标题1至100字，正文1至5000字；接收人1至100项，去重后仅向明确选择的人发送。任一收件人不合法整批拒绝。

成功data为通知ID。超时重试必须复用requestId、类型、正文、标题和接收人；同一发送人的同requestId返回原ID，修改类型也会返回409。重试不会绕过实时发送权限。

## 现有响应新增字段

`GET /page?sent=false&pageNumber=1&pageSize=20`、`GET /detail?id=99` 的每条通知新增：

| 字段 | 类型 | 含义 |
|---|---|---|
| noticeType | string | LIGHT或STRONG；历史数据归一为LIGHT |
| confirmedAt | string或null | 当前接收人的首次明确确认时间；未确认或轻通知为null；已发送列表该字段无接收人含义，应查回执 |

既有 `id,title,content,senderName,createTime,readAt,businessType,businessId,businessVersion,detailPath,actionPath` 保持不变。正文按纯文本渲染，不执行HTML。
`GET /receipts?id=99` 仅发送者可用，每项为 `{recipientId,name,readAt,confirmedAt}`，接收人相互隔离。

## 拉取待确认强提醒

`GET /pending?pageNumber=1&pageSize=20`

```json
{"code":1000,"data":{"list":[{"id":99,"title":"营业安排确认","content":"请核对明日安排。","senderName":"运营人员","createTime":"2026-11-09 20:00:00","readAt":null,"noticeType":"STRONG","confirmedAt":null,"businessType":null,"businessId":null,"businessVersion":null,"detailPath":null,"actionPath":null}],"total":1,"pageNumber":1,"pageSize":20}}
```

只返回当前接收人未确认的STRONG通知，即使readAt非空仍返回。按照通知ID升序（旧通知先处理）；pageNumber>=1、pageSize为1至100。确认后集合会变化，队列消费者应重新拉取第1页，避免翻页跳过数据；无数据list为空、total为0。读取此接口不会修改已读/确认状态。

## 明确确认

`POST /confirm`，请求 `{"id":99}`。成功data为更新后的通知详情，confirmedAt非空，readAt若原为空则同时赋值；已有readAt保留。

- 必须是当前接收人，发送人没有接收记录也不能代确认；非收件人返回404。
- 重复确认幂等，保留第一次confirmedAt，无需requestId。对LIGHT调用返回业务错误，轻通知使用原/read即可。
- 显示弹窗本身不确认。`POST /read`及任何纯已读动作不等于确认，不能因此从强提醒队列移除。
- 确认超时可用同一ID重试；成功响应前不能当作已确认。刷新、重新登录以后以服务端confirmedAt为准。

## 客户端弹窗接入

登录完成、页面回到前台时补拉；前台可每30秒轮询。一次展示一个待确认强提醒，展示发送人、时间、标题、正文及“我知道了”。点击后调用/confirm，成功再显示下一条；失败保留当前通知并允许重试。不要清空正在编辑的表单，也不要重建整个工作页面。

账号切换清空旧队列，丢弃旧账号请求响应；后台停止主动弹窗。多标签页协调展示并同步确认：统一管理端使用Web Locks（支持时）与storage事件，随后重查服务端。无Web Locks、网络故障、同时打开窗口等情况下不保证严格只弹一次，但确认接口保持幂等。

旧移动客户端仍可通过原列表和详情读取两类通知，但不具有强提醒弹窗或确认交互；未确认提醒将持续留在/pending。移动端前端需按本节接入，不能把本次后端交付视为手机弹窗已完成。强提醒不是短信、微信订阅或操作系统推送。

## 部署

先更新数据库再启用新后端/前端。开发环境开启AutoTable时会添加 `workspace_notice.notice_type` 和 `workspace_notice_recipient.confirmed_at`；关闭自动建表的环境执行 [幂等增量迁移](../deploy/notice-types-20261109.sql)。脚本不删除历史数据，可重复执行。后端需重启，管理端需重新构建部署并刷新。原AI改动保留，本次没有推送、打包Docker或修改移动端源码。
