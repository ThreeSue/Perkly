# 用户端复用商家入驻接口：前端操作注意事项

日期：2026-10-27。交接对象：客户端小程序前端。完整请求与响应见 [商家入驻接口文档](商家入驻接口文档-20261027.md)。

**目标：在用户端增加商家申请及进度查询，复用核销端已接入的同一套后端接口，不另建一套用户端专用入驻接口。** 保留用户端当前页面风格和正常登录、购券、券包等功能。

## 一、前端需要增加什么

1. 在用户端合适位置提供“申请商家入驻”“查询入驻进度／领取营业码”入口。两者均允许游客使用，不能先要求注册或登录普通用户。
2. 申请页分两步：验证申请手机号 → 填商家名称、两级行业分类、联系人、选填简介 → 提交审核。
3. 进度页：验证原手机号 → 展示该手机号的多份申请 → 选择一份查看详情 → 按状态展示等待、驳回重提、营业码或已开通提示。
4. 审核通过后仅展示营业码，引导去商家管理网页端开通OWNER。用户端不新增经营账号密码、激活、建店或核销功能。

登录用户也允许申请；申请手机号可以由申请人自行验证，不应直接假定等于当前用户账号的绑定手机。申请归属始终由短信验证凭证确定。

## 二、接口照用这一套，别换成普通用户认证接口

| 步骤 | 使用接口 |
|---|---|
| 图形验证码 | GET `/merchant/auth/captcha` |
| 行业分类 | GET `/merchant/auth/registrationCategories` |
| 发送短信 | POST `/app/merchant/onboarding/smsCode` |
| 验证短信 | POST `/app/merchant/onboarding/verify` |
| 首次申请 | POST `/app/merchant/onboarding/submit` |
| 申请列表 | POST `/app/merchant/onboarding/list` |
| 单份详情/领取码 | POST `/app/merchant/onboarding/info` |
| 驳回重提 | POST `/app/merchant/onboarding/resubmit` |
| 重新发码 | POST `/app/merchant/onboarding/renewCode` |

不要把这些步骤替换成普通用户注册、短信登录或绑定手机号接口。入驻验证不会创建普通用户，不应为了申请写入普通用户登录状态。

路径带 `/merchant` 不代表需要商家经营账号；路径带 `/app` 也不代表必须有APP用户Token。

## 三、最重要：入驻凭证与用户登录态分开

- 上表9个请求均走公共请求通道，不附带已有普通用户或员工的 `Authorization`，也不触发普通用户Token刷新。
- 短信验证返回的 `onboardingToken` 放在独立入驻状态中，仅在后续JSON请求体传入；不要保存成普通用户 `token`，不要覆盖当前登录用户。
- 入驻凭证过期只清理入驻状态，引导验证原手机号继续查询；不能因此清空普通用户账号或跳到普通用户登录页。
- 普通用户退出登录、切换账号或业务请求401，也不要把另一种Token填入入驻请求。页面隐藏/切换手机号后，丢弃旧请求的迟到结果。
- 不将凭证、营业码或密码放进URL、控制台、埋点或持久存储。营业码仅本人详情展示，不缓存为可长期使用的登录资料。

接手时检查用户端实际网络封装：若它会自动带用户Token或强制登录，应增加明确的公共请求选项，或为入驻使用独立的请求适配器。**不能直接套用要求用户登录、自动加Authorization的交易请求函数。**

路由放行仅限新增的申请和查询页面；购券、券包、订单等原有鉴权规则保持。

## 四、提交字段与分类选择

首次提交仅发送：

```json
{
  "onboardingToken":"短信验证返回的凭证",
  "requestId":"onboard_client_20261027_000001",
  "merchantName":"商家名称",
  "categoryId":11,
  "contactName":"联系人姓名",
  "introduction":"选填简介"
}
```

其中分类ID是示例，必须来自实际分类接口。重提使用同样资料字段，再增加 `applicationNo`，调用resubmit。

- 商家名称最多100字、联系人最多50字、简介最多2000字；不要沿用核销端旧表单40字等旧限制。
- 不收地址、地图位置、经纬度、首店、经营账号密码或营业执照上传。不另传手机号决定申请归属。
- 分类接口返回平铺数组；按parentId组织成两级，先一级行业再对应子类，显示名称路径，只提交二级categoryId。
- 不将一级、二级混排在同一个单列列表，不提交中文分类名称或路径数组。
- 驳回回填商家名称读取 `snapshot.name`，或以顶层 `merchantName` 兜底。分类按snapshot.categoryId恢复父子路径。
- 历史快照可能带address；只取当前有效字段，不能将整个snapshot直接展开后重提。

## 五、查询状态与营业码怎么展示

| state | 用户端操作 |
|---|---|
| PENDING | 显示待审核、刷新入口，不开放经营权限 |
| REJECTED | 展示reason，允许编辑并重提，保留applicationNo |
| APPROVED | 展示本人详情中的营业码、有效期和复制，引导网页开通 |
| CODE_EXPIRED | 提供重新获取营业码 |
| ACTIVATED | 显示已开通，去商家管理网页端正常登录；不再发码 |

只按 `state` 控制业务，不单凭reviewStatus=2就显示“账号已开通”。营业码不是普通用户优惠券码，不放入“我的券”，不生成可供消费核销的券或订单。

列表最多100条摘要，不返回可用营业码和完整驳回资料；领取码、看原因及修改前必须查info。详情仅当前轮次，不自行拼造完整审核历史。

营业码有效7天、成功使用一次；网页需验证申请时同一手机号，设置账号密码后一次开通OWNER。用户端不要调用 `/merchant/auth/activate`、旧 `/merchant/auth/register` 或旧密码重提入口。

## 六、网络异常别重复申请

- 新申请生成一次requestId，连点防重；提交超时保留原资料和标识，查询或沿用原标识重试。
- 不确定是否受理时，不清空表单、换requestId再次申请。页面重启丢失临时标识时，先验证原手机号查询已有申请。
- 重提响应未知先查info；已经PENDING就表示已重提，不能再重提一次。
- 重发码前后均以info核实，已有新的有效码则不自动再次重发，避免使刚拿到的码失效。
- 凭证30分钟过期后重新验证原手机号继续处理；不要误当成要新建一个商家。
- JSON `code=1000` 才是成功；HTTP 200中的业务失败仍需显示message并保留可恢复的输入。

## 七、复用核销端代码时的边界

可参考新仓库main提交0506a56中 `apps/merchant` 的入驻API、独立内存状态、共用资料表单、两级分类处理和状态展示。

不要整包覆盖用户端，也不要直接照搬核销端员工身份、测试经营账号、路由守卫、导航外壳、AppID或开发后端地址。复用协议和独立业务逻辑，按用户端现有组件风格接页面；复制带 `@/` 的模块时核对别名导入及依赖，确保没有暗中依赖merchant-auth或staff/me。

本次核销端推送仅包含 `apps/merchant`，根目录测试和独立文档未随该提交上传。需要参考测试时由本地交付，不能误以为远程一定已包含。

## 八、交付前至少验证这些情况

1. 游客直接打开申请/查询，无需普通用户登录；不自动发送短信。
2. 已登录用户申请后，原用户Token、昵称、券包和购券功能不被清空或替换。
3. 两级行业切换正确，只发送二级ID；请求没有地址、首店、密码或旧Authorization。
4. 同一手机号查询多份申请，另一手机号不能看到原申请；凭证过期重新验证后仍能查询。
5. 待审、驳回重提、审核通过领取码、码过期重取、已开通五种状态均正确。
6. 超时重试不重复申请，换手机号/离开页面后旧响应不串入当前页面。
7. 微信小程序编译、输入框和分类选择、模拟器及真机可达后端分别检查；真实短信、提交申请等写操作使用约定测试资料。

核销端用户反馈跑通仅代表核销端已有验证结果，不能代替用户端接入后的验收。
