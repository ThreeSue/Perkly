## 1. 通用约定

- 服务根地址：开发后端默认 `http://127.0.0.1:8001`；手机必须换为设备可访问的电脑IP或服务器域名。IP随网络变化，不把历史IP当作固定地址。
- POST默认JSON；GET参数放Query。除文件上传外 `Content-Type: application/json`。
- 普通用户使用APP Token；商家核销使用MERCHANT Token。请求头为 `Authorization: 原始Token`，**不加Bearer**，不能跨端复用令牌。2026-10-30新增的账号类型STORE不是Token类型：门店账号仍使用MERCHANT Token；普通用户不改为STORE，也不用接后台动态菜单。
- 核销端登录/刷新可选增加 `accountType:"STORE"`，经营请求可选发送 `X-Workspace: STORE`；不传仍兼容旧移动端。若发送，必须与真实账号类型一致，不能因为Token类型为MERCHANT就把请求头也写成MERCHANT。公共入驻请求不沿用经营身份头。
- 游客登录、验证码、入驻凭证接口不发送旧Authorization；公开浏览不要求登录。地图代理要求APP登录。
- JSON成功：`{"code":1000,"message":"success","data":...}`。业务失败读message；同时处理HTTP401/403，不能仅凭HTTP200判成功。data可能为null。
- 已鉴权的用户/员工经营请求遇HTTP401或业务401，可按对应端协议尝试刷新一次，失败则退出对应会话；403不循环刷新。公共入驻请求不触发普通用户/员工刷新，入驻凭证过期仅重新验证申请手机号。
- 本文优惠券、交易、核销及消费账单金额均为**整数分**；990表示9.90元。折扣 `discountRate=8.8` 表示8.8折，不除以100。
- 业务时区Asia/Shanghai。交易时间通常为 `yyyy-MM-dd HH:mm:ss`；消费账单Date字段依部署的统一序列化配置，解析时不要假设本机时区。
- 业务分页一般为请求page/size，响应 `{"list":[],"pagination":{"page":1,"size":20,"total":0}}`；框架附录的CRUD可能使用另一种分页结构，不混用。
- `couponTemplateId`是券模板；`customerCouponId`/券包id是具体持券；`publicationId`是发布记录；`code`是券码。购券订单和消费账单是两类业务，id/orderNo不能混用。
- merchantId、operatorId、customerId、订单号、优惠金额、状态以服务端可信身份和计算结果为准，不让客户端任意指定。
- 页面展示名称和中文状态；ID仅用于关联。私有详情与历史结果在退出/切换账号后清除，忽略迟到的旧会话响应。

### 当前核销业务口径

购券使用模拟支付；到店消费补款使用**商家人工确认线下已收款**。这不是微信扣款接口。内容类券直接兑换，无本次补款。尚未提供普通顾客“不用券直接在线支付消费单”的接口，不据此前讨论自行增加。

## 2. 用户认证与登录

文档核对日期：2026-10-25；协议来源更新日期：2026-10-20。

### 图片验证码

```http
GET /app/user/login/captcha?type=base64&width=150&height=50
```

`type`、`width`、`height` 为当前用户端请求必填参数，分别传 `base64`、150、50。尺寸也可以按 UI 调整。

响应：

```json
{
  "code":1000,
  "message":"success",
  "data":{"captchaId":"图片验证码ID","data":"data:image/png;base64,图片内容"}
}
```

图片使用 `data.data` 显示，保留同次返回的 `captchaId`。刷新图片时清空旧图片验证码输入。用户图片验证码与管理员图片验证码分别从各自端点获取。

### 发送短信验证码

```http
POST /app/user/login/smsCode
```

```json
{"phone":"13800000000","captchaId":"图片验证码ID","code":"1234"}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| phone | string | 是 | 中国大陆11位手机号 |
| captchaId | string | 是 | 本次图片验证码的 ID |
| code | string | 是 | 图片验证码内容；不是短信验证码 |

成功响应为通用成功格式，无短信验证码返回。图片验证码通过并发送成功后，本次图片验证码会被消费；后续填写短信码即可，重新发送时获取新的图片验证码。

当前短信规则：6位数字，5分钟有效，同手机号60秒发送间隔；成功验证后不能重复使用，连续错误5次使本地验证记录失效。验证码由阿里云短信认证服务生成并核验，短信签名当前为“恒创联众”。发送接口成功表示请求已受理，实际送达以手机收信及服务商回执为准。

### 短信登录

```http
POST /app/user/login/phone
```

```json
{"phone":"13800000000","smsCode":"123456"}
```

两个字段均为必填 string。未注册手机号验证成功会自动创建普通用户账号；该账号尚未设置密码时，可登录后在设置页设置密码。

### 手机号与密码登录

```http
POST /app/user/login/password
```

```json
{"phone":"13800000000","password":"ExamplePass123"}
```

两个字段均为必填 string。手机号就是账号；不传 `username`。账号不存在、未设置密码、密码错误或账号不可用时拒绝登录。密码原样提交，不在前端做 MD5/BCrypt；通过 HTTPS 部署后传输，后端负责密码哈希存储。

### 显式注册

```http
POST /app/user/login/register
```

```json
{"phone":"13800000000","smsCode":"123456","password":"ExamplePass123"}
```

三个字段均为必填 string。新密码8至32位，不包含空白字符；后端还限制 UTF-8 编码不超过72字节。确认密码只用于前端校验，不传后端。

注册成功即返回登录 Token。已有手机号拒绝重复注册，不覆盖密码；已通过短信登录自动创建的账号，应登录后设置密码。

### 登录／注册共同返回格式

```json
{
  "code":1000,
  "message":"success",
  "data":{
    "userId":42,
    "token":"访问Token",
    "expire":7200,
    "refreshToken":"刷新Token",
    "refreshExpire":604800
  }
}
```

`expire` 和 `refreshExpire` 为有效时长，单位秒，示例数值不代表固定配置。使用实际响应值。成功后先保存 Token，再调用个人资料接口；不要把密码或短信验证码存入用户缓存。

普通用户正式登录响应还包含 `userId`（integer）。账号页面发起绑定时，前端用它确认登录结果仍属于当前手机号账号，避免意外切换到另一个微信已绑定账号。

### 刷新用户 Token

```http
POST /app/user/login/refreshToken
```

```json
{"refreshToken":"当前刷新Token"}
```

返回本章登录响应格式，更新访问 Token 与有效时长。刷新失败进入重新登录流程。前端应在当前项目请求层封装此调用。

### 微信小程序登录与首次绑定手机号（2026-10-13新增）

`POST /app/user/login/mini` 请求：`{"code":"本次uni.login取得的临时code"}`。不传客户端 openid，也不需要 encryptedData/iv；身份由后端使用 WxJava 向微信兑换。

已绑定手机号时返回本章登录响应中的普通用户 Token；未绑定时返回：

```json
{"code":1000,"message":"success","data":{"bindingRequired":true,"bindingToken":"随机临时凭证","bindingExpire":600}}
```

未绑定时没有访问 Token，也不会立即创建新的 user_info 账号。bindingToken 只放页面内存中，不放 URL、长期缓存或日志，10分钟过期。前端弹出手机号验证框，复用本章图片与短信验证码接口获取短信验证码，然后调用：

```http
POST /app/user/login/bindWechatPhone
Content-Type: application/json

{"bindingToken":"微信登录返回的临时凭证","phone":"13800000000","smsCode":"123456"}
```

三个字段均为必填 string。绑定凭证关联后端已核验的微信记录；短信确认该手机号的持有人。手机号没有账号时创建或补全账号，成功返回本章登录Token 格式；已有不同的手机号账号时，短信核验后先返回确认信息，尚不保存关联或签发登录 Token：

```json
{
  "code":1000,"message":"success",
  "data":{
    "confirmationRequired":true,
    "confirmationToken":"随机确认凭证",
    "confirmationExpire":600,
    "canUseWechatProfile":true,
    "wechatProfile":{"id":11,"nickName":"微信账号昵称","avatarUrl":"https://example.com/wx.png"},
    "phoneProfile":{"id":42,"nickName":"手机号账号昵称","avatarUrl":null,"phoneMasked":"138****0000"}
  }
}
```

两份资料只在短信验证通过后展示。微信侧没有已保存资料时对应字段可能为空，canUseWechatProfile=false，前端不允许选择空资料覆盖原账号。确认凭证10分钟有效，只保留在页面内存中；此时旧 bindingToken 已消费。用户选择保留来源后调用：

```http
POST /app/user/login/confirmWechatBinding
Content-Type: application/json

{"confirmationToken":"上一步的确认凭证","profileSource":"phone"}
```

profileSource 只接受 phone（保留手机号账号资料）或 wechat（使用微信对应账号已有的昵称头像）。选择微信资料时只替换其中非空的昵称、头像；不修改手机号账号ID、密码及其他业务数据。确认成功才保存微信关联、消费确认凭证并返回本章登录Token；取消确认不保存关联。

拒绝过期／不存在／重复使用的绑定凭证、错误短信码、不可用账号、手机号已绑定另一微信，以及微信已绑定其他手机号。账号创建／绑定放在同一数据库事务中；数据库写入失败后可能需要重新获取短信码。当前按一个平台账号绑定一个微信实现。

关联存于 user_wx 新增的 userId 字段，并建立唯一索引；保留对旧版 user_info.unionid 的读取兼容。旧微信无手机号记录遇到已有手机号账号时，将微信关联到手机号账号；不删除旧记录，也不自动迁移旧记录的其他业务数据。后端重启时需由当前 AutoTable 配置同步字段和索引。当前为单实例同步保护，多实例部署需增加分布式并发控制。

首次绑定页面是否已接入，以当前前端版本为准。实际微信身份兑换、短信收取和数据库绑定仍需真实环境联调。

## 3. 用户资料与账号安全

文档核对日期：2026-10-25；协议来源更新日期：2026-10-20；2026-10-25核对会话规则。

### 获取个人资料

```http
GET /app/user/info/person
Authorization: <用户Token>
```

`data` 为用户资料对象，主要使用 `id`、`phone`、`nickName`、`avatarUrl`、`gender`、`status`、`createTime`、`updateTime`。密码不返回；前端按实际返回字段渲染，部分可选字段可能为空。

当前状态值：1正常、0禁用、2注销。手机号展示可脱敏，发送修改密码短信使用后端返回的完整绑定手机号。

### 更新个人资料

```http
POST /app/user/info/updatePerson
Authorization: <用户Token>
```

```json
{"nickName":"券管家用户","avatarUrl":"https://example.com/avatar.png","gender":0}
```

当前接口仅接受 `nickName`（string）、`avatarUrl`（string）、`gender`（integer）。用户 ID 由 Token 确定，不接受通过此接口修改手机号、密码或账号状态。当前编辑页面应带上这三项的现有值与修改值；不假设遗漏字段一定被保留。后端成功时 `data` 为更新操作的 boolean 结果，前端应确认成功并重新获取资料。

### 设置／修改密码

```http
POST /app/user/info/updatePassword
Authorization: <用户Token>
```

```json
{"password":"NewExamplePass123","code":"123456"}
```

`password` 为新密码，`code` 为新获取的短信验证码，均为必填 string；此处不是 `smsCode`。不传手机号或用户 ID，后端从当前登录用户读取绑定手机号并核验。

调用顺序：获取用户资料 → 为绑定手机号获取图片验证码与新短信验证码 → 输入新密码和确认密码 → 提交本接口。登录时已经使用的短信码不能复用。

成功响应为通用成功格式。前端清空密码和验证码输入，结束倒计时并提示成功。当前凭据版本机制使旧访问/刷新令牌在密码变更后失效，应清除本地旧登录凭证并重新登录。入口：“我的 → 设置 → 账号 → 设置／修改密码”。

### 账号与绑定状态

登录后 `GET /app/user/info/account`，使用用户 Token。返回当前账号的 id、nickName、avatarUrl、phoneBound、phoneMasked、wechatBound、passwordSet。其中绑定与密码状态均为 boolean；不返回密码哈希、openid 或 unionid。

“我的 → 设置 → 账号”显示绑定状态和密码设置状态，提供绑定手机号／微信及设置／修改密码入口。已绑定手机号账号从此处绑定微信时，手机号固定为当前账号，仍需短信验证；如果微信已关联另一个账号，前端拒绝切换当前登录账号。

### 忘记密码接口

### 优惠券列表

```http

{"page":1,"size":20,"storeId":101,"type":"CASH"}
```

| 参数 | 必填 | 说明 |
|---|---|---|
| page、size | 否 | 分页 |
| keyword | 否 | 券名称或商家名称的包含搜索，最多100字 |

#### 公开范围

查询复用`coupon_template、coupon_publication、coupon_store、store、merchant_info`等已有表。服务端固定要求：

1. 券模板启用、所属商家启用。

| 字段 | 说明 |

| merchantId、merchantName、merchantLogo | 所属商家公开信息 |
| categoryId、categoryName | 商家行业分类 |
| name、type、typeText、cover、description | 券名称、类型、类型文字、封面、完整使用说明 |
| salePrice | 售价，整数分；0表示售价为零，实际领取需调用claim接口 |
| minSpend、discountAmount、deductAmount、maxDiscount | 门槛、满减金额、抵扣额、最高优惠；整数分，不适用时为null |
| discountRate | 折扣数，例如8.80表示8.8折，不适用时为null |
| scopeType | 0商家全部营业门店；1指定门店 |
| issueLimit、issuedCount、remainingStock | 发行上限、已发放数量、剩余数量；不限量时issueLimit和remainingStock为null |
| perCustomerLimit | 每位顾客领取／购买总量上限，不表示当前用户剩余可领数量 |
| allowCombine | 0不可同享其他优惠，1允许同享 |
| saleStartTime、saleEndTime | 可领取／购买起止时间 |

| saleState | 文字 | 条件及优先级 |

| SOLD_OUT | 已售罄 | 有发行上限且已发放数量达到上限 |
| NOT_STARTED | 未开始 | 领取购买开始时间未到 |
| AVAILABLE | 可领购 | 通过上述时间和库存判断；实际领购仍由下单/领取接口重新校验 |

### 模拟支付、取消与订单查询

`POST /app/order/simulatePay`：

```json
{"id":201,"result":"SUCCESS"}
```

`result` 默认 `SUCCESS`，也可传 `FAILED`。这是演示用模拟支付，**尚未接入微信支付、支付宝或真实资金结算**。

- 成功：同一事务内生成对应数量的持券、唯一券码和真实 PNG 二维码，增加已发行数量，再将订单改为 `PAID/SUCCESS`。任一步骤失败，整笔回滚。
- 支付失败：订单改为 `FAILED/FAILED`，不发券；需重新下单。
- 已支付订单再次提交 `SUCCESS` 返回原结果，不重复发券。
- 超时、取消、下架、售罄、累计超限、模板规则版本发生变化等情况不能支付。
- 不接受客户端提交售价、总金额或优惠金额，金额由后端模板计算。

返回订单详情，`couponIds` 如 `[401,402]`；这些是持券 ID，用于券包详情和二维码接口，不是模板 ID。

| 状态 | 中文 | 说明 |
|---|---|---|
| PENDING | 待支付 | 尚未超时 |
| PAID | 已完成 | 支付/免费领取成功，已发券 |
| CANCELLED | 已取消 | 用户取消 |
| FAILED | 支付失败 | 模拟支付失败 |
| EXPIRED | 已超时 | 待支付且已过失效时间，查询时计算 |

分页列表是订单摘要，不含 `items`、`couponIds`。`GET /app/order/info?id=201` 返回上面的完整详情。只能访问当前用户自己的订单。

| 参数 | 必填 | 规则 |
| --- | --- | --- |
| longitude | 是 | number，经度 -180 至 180 |
| latitude | 是 | number，纬度 -90 至 90 |
| radiusMeters | 否 | 搜索半径，单位米；默认 10000，范围 1 至 100000 |
| page | 否 | 默认 1，大于 0 |
| size | 否 | 默认 20，范围 1 至 100 |
| keyword | 否 | 最多 100 字，匹配门店名、商家名、地址 |
| merchantId | 否 | 所属商家 ID，大于 0 |
| categoryId | 否 | 商家行业分类 ID，大于 0；包含该分类及直接下级，不是门店类型 ID |

默认参数建议省略或传有效值，不传 null 代替默认值。所有坐标均为 **GCJ-02**，不要把 WGS-84 或 BD-09 直接混用。经度和纬度不能写反；零值本身合法，不用 `if (!longitude)` 判断是否有定位结果。

#### 完整成功响应示例

```json
{
  "code": 1000,
  "message": "success",
  "data": {
    "list": [
      {
        "id": 101,
        "name": "示例咖啡店",
        "merchantId": 1,
        "merchantName": "示例商家",
        "storeTypeId": 1,
        "storeTypeName": "直营店",
        "cover": null,
        "address": "福建省福州市示例路1号",
        "phone": "13800000001",
        "businessHours": "09:00-21:00",
        "longitude": 119.201,
        "latitude": 26.101,
        "status": 1,
        "statusText": "营业中",
        "located": true,
        "locationStateText": "已设置位置",
        "distanceMeters": 149.5
      }
    ],
    "pagination": { "page": 1, "size": 20, "total": 1 }
  }
}
```

`distanceMeters` 是数值、单位米，代表球面直线距离，不是步行/驾车距离或预计到店时间。示例距离只是格式示意。显示可按项目规则转换为米或千米，保留原值用于计算。`pagination.total` 是符合条件的总条数，不是总页数。

列表字段：id/name 为门店标识与名称；merchantId/merchantName 为所属商家；storeTypeId/storeTypeName 为门店类型；cover 为可空封面；address、phone、businessHours 为展示资料；longitude/latitude 为坐标；status/statusText 为状态编码与文字；located/locationStateText 为位置状态；distanceMeters 为距离。

只返回坐标有效、门店营业且所属商家启用的数据。后端先按半径过滤、按距离升序、同距离按门店 ID 升序，再分页。没有附近门店时返回空列表和 total=0，不自动混入远处门店。未补录坐标的门店不会进入附近结果。

#### 首页与列表接入顺序

1. 首屏广告独立加载，不等待定位，不强迫游客登录。
2. 没有位置时先使用已有 `/app/merchant/store/page` 浏览普通门店。用户主动定位或选择地点后，保存 GCJ-02 经纬度，再调用 nearby；不能只改顶部城市文字。
3. 定位成功后显示附近结果与距离；定位拒绝、失败或不可用时回到普通列表，明确当前没有使用距离排序，不传虚构或默认坐标。
4. 切换位置、分类、关键词或半径时，页码重置为 1，清空旧页，重新请求。翻页只追加同一组筛选结果，丢弃较早请求的迟到响应，避免 A 城市结果覆盖 B 城市。
5. 定位成功但结果为空时保留“附近暂无门店”的真实状态；可以由用户主动切换普通浏览或扩大半径，不能把全平台结果伪装为附近。
6. 点门店进入已有详情页。不把附近接口响应强行当作普通列表的全部字段，两者分别适配；更多详情按已有 info 接口读取。

### 8.2 自定义选址需要的腾讯地点接口

这组接口查询腾讯地点库，不是查询平台商家或平台门店；需要已登录用户访问 Token。游客不调用这组接口，可按平台能力使用原生选址或保留普通门店浏览。

#### 8.2.1 地点搜索

`GET /app/merchant/map/suggest?keyword=闽侯县人民政府&region=福州`

keyword 必填，1 至 100 字；region 可选，最多 50 字。指定城市仅返回该城市结果；不指定则全国搜索。Query 参数由请求库编码，不手工拼接未编码的中文和特殊字符。

成功 `data`：

```json
{
  "coordinateSystem": "GCJ-02",
  "total": 1,
  "list": [
    {
      "id": "腾讯POI标识",
      "title": "地点名称",
      "address": "详细地址",
      "longitude": 119.2,
      "latitude": 26.1,
      "province": "福建省",
      "city": "福州市",
      "district": "闽侯县"
    }
  ]
}
```

最多 20 条，无分页，不代表全部地点。输入防抖 300 至 500ms，避免重复请求并丢弃过期响应。选择后先预览地点，用户确认后再用于附近门店查询。

#### 8.2.2 地址转坐标

`GET /app/merchant/map/geocode?address=福建省福州市闽侯县人民政府&region=福州`

address 必填，1 至 500 字；region 可选，最多 50 字。成功 data 见下方。

#### 8.2.3 坐标转地址

`GET /app/merchant/map/reverseGeocode?longitude=119.2&latitude=26.1`

longitude、latitude 必填，范围与附近查询一致。两种解析成功 `data` 均为：

```json
{
  "coordinateSystem": "GCJ-02",
  "address": "地址文字",
  "longitude": 119.2,
  "latitude": 26.1,
  "province": "福建省",
  "city": "福州市",
  "district": "闽侯县"
}
```

区划字段可能为空；地址转坐标的 address 保留输入地址，逆解析的 address 为服务返回地址。这些接口只查询、不写入门店位置，也不自动更新用户资料。

不把后端腾讯 Key、签名密钥或 sig 放到前端，不自己拼腾讯 WebService 请求替代后端。若只用原生定位加附近门店列表，不需要为了列表额外嵌入网页地图。需要网页底图时使用对应前端 SDK 配置，与上述后端接口密钥区分。

网络失败、未配置、授权或配额异常时显示后端 message，支持重试，保留普通浏览。历史出现过腾讯服务 121 错误，本次未重新调用上游，是否已恢复需联调现场确认。平台附近查询在数据库计算距离，不依赖腾讯地点服务可用性。


#### 8.2.4 GPS转腾讯地图坐标（2026-10-30新增，按需接入）

`GET /app/merchant/map/translateGps?longitude=119.2&latitude=26.1`

认证：APP Token，沿用原始Authorization。longitude、latitude必填、为有限数字，经度-180至180、纬度-90至90；参数分别是经度和纬度，不能互换。输入为真实GPS/WGS-84坐标，输出为GCJ-02。

成功响应示例（转换后的数值仅示意，不是转换精度样本）：

```json
{
  "code":1000,
  "message":"success",
  "data":{
    "coordinateSystem":"GCJ-02",
    "address":null,
    "longitude":119.205,
    "latitude":26.103,
    "province":null,
    "city":null,
    "district":null
  }
}
```

本接口只转换坐标，不获取设备位置、不解析地址、不保存用户或门店资料。要地址时，把转换后的坐标传给8.2.3逆解析。地址/区划在转换响应中为空，兼容null或省略。

- 小程序已经通过 `uni.getLocation({type:"gcj02"})` 或原生选址获得GCJ-02时，直接用于nearby，不再转换，避免二次偏移。
- 仅在位置来源明确为GPS/WGS-84时调用；不确定来源时先核对定位API的坐标类型，不将任何经纬度一律当GPS。
- 原生定位可让游客按既有能力浏览附近；此后端地图代理仍要求APP登录，不应为了转换而把原本可用的游客附近浏览强制改成登录。
- 未配置地图、腾讯授权/配额或网络异常时显示message，不把原始GPS坐标冒充GCJ-02继续查询；可回到普通门店浏览，或使用能直接返回GCJ-02的原生定位能力。

## 9. 游客商家入驻申请

核对更新：2026-10-30（包含营业执照号补充）。两个移动端复用同一套公共接口，不另建用户端专用入驻接口。以下已合并当前契约、用户端复用注意事项及核销端实际修改，本文可直接交给两个移动端前端。

独立交付版：[商家入驻接口文档](商家入驻接口文档-20261027.md)；[用户端复用操作注意事项](用户端复用商家入驻接口-前端操作注意事项-20261027.md)。

### 9.1 最终流程与各端职责

**移动端验证手机号 → 提交商家资料 → 平台审核 → 移动端领取营业码 → 网页端验证同一手机号、设置账号密码并开通OWNER → OWNER按平台已授权功能创建门店。**

| 业务端 | 负责内容 |
|---|---|
| 客户端小程序 | 游客申请、查询进度、驳回重提、领取及重取营业码 |
| 商家核销端小程序 | 同样开放游客申请和查询；已有店长/员工经营功能独立保留 |
| 商家管理网页端 | 停止直接申请，提示前往小程序；保留营业码开通、账号登录、开通后的建店和人员管理 |
| 平台运营端 | 使用已有审批中心审核商家申请 |

必须区分：

- 申请阶段收商家资料及营业执照号licenseNumber，不收地址、经纬度、首店名称、经营账号或密码；不要求上传营业执照图片。营业执照号是文字编号，与图片上传、营业码是三个不同概念。
- 短信验证不注册普通用户，不要求先登录普通用户或员工账号。
- 审核通过只发营业码，不创建正式商家、OWNER或门店，不开放店员经营权限。
- 网页确认开通才创建商家及OWNER账号；不会自动创建门店，不会自动指定默认门店，也不会直接返回经营Token。新增商家的经营功能还要由运营授权，ACTIVATED不等于所有业务权限已经开放。
- 营业码只需成功使用一次。后续账号密码登录，不再输入营业码。
- 地址、GCJ-02经纬度属于后续创建的门店。建店使用既有 `/merchant/workspace/store/save`，不属于本次入驻提交。

### 9.2 公共约定

#### 服务地址与返回包装

各端配置实际可访问的后端基地址，下文仅列路径。手机真机的 `127.0.0.1` 指手机自身，不能直接作为电脑后端地址；局域网地址应按当时环境核对。

POST使用 `Content-Type: application/json`。成功统一包装：

```json
{"code":1000,"message":"success","data":{}}
```

失败判断 `code != 1000`，显示 `message`；不能仅凭HTTP 200判断成功。无数据接口的 `data` 可能为空或省略，不依赖其中字段。

日期按当前后端配置为北京时间，格式 `yyyy-MM-dd HH:mm:ss`。可空字段兼容 `null` 或未返回；不要将空营业码当成字符串展示。

#### 入驻凭证与经营Token严格分开

本文验证码、分类、手机号验证、申请、查询、重发及开通接口均是公共接口，**不要附带旧普通用户/员工的Authorization**。入驻身份依据是JSON请求体中的 `onboardingToken`。

- 凭证由手机号短信验证返回，64位小写十六进制，有效1800秒（30分钟）。
- 只用于手机号入驻及开通，不能拿去访问用户资料、员工身份或经营接口。
- 查询/重提/重发只允许操作该手机号自己的申请；不能通过另传手机号改变归属。
- 过期后重新验证原手机号，取得新凭证继续查询，无须重新申请。
- 各端分别验证手机号，独立获取凭证，不跨应用传递旧凭证。
- 凭证、营业码、密码不进URL、日志或Git，不新增持久化敏感凭证。路由只传无敏感信息的页面模式参数。
- 一个手机号可以申请多个不同商家，不能将“同手机号”视为唯一商家。

以下JSON均为结构示例，手机号、分类ID、凭证、申请号等须替换成实际获取的值；不是可直接登录的测试数据。

### 9.3 接口总览

| 方法 | 路径 | 调用方/用途 |
|---|---|---|
| GET | `/merchant/auth/captcha` | 各端获取图形验证码 |
| GET | `/merchant/auth/registrationCategories` | 移动端获取可申请行业分类 |
| POST | `/app/merchant/onboarding/smsCode` | 各端发送手机号验证码 |
| POST | `/app/merchant/onboarding/verify` | 各端验证短信、获取独立凭证 |
| POST | `/app/merchant/onboarding/submit` | 两个移动端首次申请 |
| POST | `/app/merchant/onboarding/resubmit` | 两个移动端驳回重提 |
| POST | `/app/merchant/onboarding/list` | 查询本人多份申请摘要 |
| POST | `/app/merchant/onboarding/info` | 查询本人单份详情及可用营业码 |
| POST | `/app/merchant/onboarding/renewCode` | 已通过未开通申请重新发码 |
| POST | `/merchant/auth/activate` | 仅商家管理网页端一次开通OWNER |

`/app` 路径前缀不限制核销端调用，也不代表需要APP用户Token。

### 9.4 获取图形验证码

`GET /merchant/auth/captcha`，无参数、不带Authorization。

成功 `data`：

```json
{"captchaId":"图片验证码ID","data":"data:image/png;base64,图片内容"}
```

`data.data`直接作为图片源。发送短信时将用户填写的图片字符作为 `verifyCode`，不要误传为短信码。失败后允许重新获取图片；不要用本地测试登录的假验证码替代入驻验证码。

### 9.5 获取行业分类及两级选择

`GET /merchant/auth/registrationCategories`，无参数、不带Authorization。

成功 `data` 是平铺数组，不是树：

```json
[
  {"id":1,"name":"餐饮美食","parentId":0},
  {"id":11,"name":"龙虾烧烤","parentId":1},
  {"id":12,"name":"冰凉甜品","parentId":1}
]
```

只返回启用的分类。前端按 `parentId` 构建两级联动：

1. 第一级选择行业，例如餐饮美食。
2. 第二级只展示该行业下的分类，例如龙虾烧烤。
3. 确认后显示完整路径，请求的 `categoryId` **只提交二级ID**，示例为11，不提交路径数组或中文名称。
4. 更换一级行业后，二级选择必须重新匹配。不能沿用原行业的子类。
5. 无有效二级选项、已停用或孤立分类不能当作有效选择；历史重提按二级ID恢复路径，失效时要求重选。

这是当前前端交互要求。当前后端校验分类存在且启用，并未额外强制它必须是二级，因此前端需要维持两级选择约束。

### 9.6 发送短信验证码

`POST /app/merchant/onboarding/smsCode`

```json
{"phone":"申请人手机号","captchaId":"图片验证码ID","verifyCode":"用户填写的图片字符"}
```

| 字段 | 必填 | 规则 |
|---|---|---|
| phone | 是 | 中国大陆手机号，匹配 `1[3-9][0-9]{9}` |
| captchaId | 是 | 上一步获取的图片ID |
| verifyCode | 是 | 图片字符，注意与smsCode区分 |

成功按 `code=1000` 判断，不依赖业务数据。用户明确点击发送后才请求，页面初始化不得自动发短信。使用原短信服务的有效期、发送间隔和限流；前端可做60秒倒计时，但最终以服务端限制为准。发送超时不要提示“已发送成功”，避免自动循环重发。

### 9.7 验证短信并取得凭证

`POST /app/merchant/onboarding/verify`

```json
{"phone":"申请人手机号","smsCode":"用户收到的6位数字短信验证码"}
```

成功 `data`：

```json
{"onboardingToken":"64位小写十六进制凭证","expiresIn":1800}
```

短信码验证成功后消费，不应重复拿同一短信码不断验证。连续错误达到服务端限制时需重新获取验证码。有效期由短信服务配置决定，不与30分钟入驻凭证有效期混淆。

### 9.8 首次提交申请

`POST /app/merchant/onboarding/submit`

```json
{
  "onboardingToken":"手机号验证返回的凭证",
  "requestId":"onboard_20261027_000001",
  "merchantName":"示例商家",
  "categoryId":11,
  "contactName":"联系人姓名",
  "introduction":"商家简介，可不填",
  "licenseNumber":"91350100123456789X"
}
```

| 字段 | 类型 | 必填 | 规则 |
|---|---|---|---|
| onboardingToken | string | 是 | 本人有效手机号凭证 |
| requestId | string | 是 | 8～64位字母、数字、下划线或短横线；前端为新操作生成 |
| merchantName | string | 是 | 非空，最多100字 |
| categoryId | number | 是 | 有效、启用的分类ID；两级选择传二级ID |
| contactName | string | 是 | 非空，最多50字 |
| introduction | string | 否 | 最多2000字；同一次重试保持原内容及空值表达 |
| licenseNumber | string | 兼容旧端可不传；新版表单要求填写 | 15或18位英文字母/数字；前端去首尾空格并转大写，后端校验长度与字符并按大写保存；不要用空字符串代替未填写 |

联系电话由凭证确定，不要另传 `phone` 或 `contactPhone` 修改归属。不要提交 `address`、坐标、门店名、username/password、licenseUrl、userId、merchantId、角色或审核状态。

成功返回下文统一申请详情，通常为 `PENDING`。同一手机号、同一requestId、相同资料的首次申请重试返回原申请，不重复创建。licenseNumber已参与同requestId资料一致性校验；结果未知时不得改编号后复用原标识。

编号开通后复制到正式商家资料并锁定，商家和运营均不能覆盖已有编号。历史未传或旧商家空值仍兼容，后续在有权管理网页一次性补录；移动端不为已开通商家提供修改编号流程。不传/null为兼容空值，传空字符串不满足Pattern校验。

#### 提交结果未知时

- 连点只允许发起一次进行中的提交。
- 超时/断网后保留原资料和requestId，查询申请或重试原操作，不更换requestId盲目新建。
- 原结果未确认前不允许修改资料后复用原requestId。
- 凭证过期后验证同一手机号，仍应尽量恢复原操作标识；若页面进程已丢失临时状态，先查询列表确认是否已受理。
- 只有用户明确申请另一个商家或确认原操作未创建申请，才开始新的申请操作。

### 9.9 查询本人申请列表

`POST /app/merchant/onboarding/list`

```json
{"onboardingToken":"手机号验证返回的凭证"}
```

成功 `data` 为数组，按申请记录倒序取最新100条，**不分页**。每项使用统一响应模型的摘要字段；不提供营业码、完整快照或驳回详情，相关字段可能为空。

```json
[
  {"applicationNo":"申请单号","submissionNo":1,"merchantName":"示例商家","reviewStatus":1,"state":"PENDING","stateText":"待审核"}
]
```

允许用户选择具体申请后调用info。无申请显示空状态，不自动创建新申请。

### 9.10 查询详情及领取营业码

`POST /app/merchant/onboarding/info`

```json
{"onboardingToken":"手机号验证返回的凭证","applicationNo":"选中的申请单号"}
```

#### 统一申请响应模型

submit、resubmit、info、renewCode、activate返回此模型；list使用其摘要。详情不是完整审核历史数组，只返回当前轮次，不能在前端伪造历次审核记录。

| 字段 | 类型/可空 | 说明 |
|---|---|---|
| applicationNo | string | 申请单号；驳回重提保留 |
| submissionNo | number | 当前提交轮次；重提递增 |
| merchantName | string | 商家名称，列表/标题可直接展示 |
| reviewStatus | number | 1待审、2通过、3驳回；与开通状态不是同一概念 |
| state | string | 统一前端状态，见下表 |
| stateText | string | 对应中文状态 |
| reason | string，可空 | 当前驳回原因，详情可返回 |
| snapshot | object，可空 | 当前提交资料快照，详情可返回 |
| activationCode | string，可空 | 本人详情且通过、未开通、未过期时才可返回 |
| codeExpiresAt | 日期，可空 | 营业码失效时间 |
| activatedAt | 日期，可空 | 成功开通时间 |
| merchantId | number，可空 | 正式开通后的商家ID，用于内部关联 |
| accountId | number，可空 | 正式开通后的OWNER账号ID，用于内部关联 |

`snapshot`当前实际字段：

```json
{"name":"示例商家","categoryId":11,"categoryName":"龙虾烧烤","contactName":"联系人姓名","contactPhone":"已验证手机号","introduction":"商家简介","licenseNumber":"91350100123456789X"}
```

licenseNumber在历史快照中可能为null或不存在；展示时使用“未填写”，不能伪造编号。驳回重提按 `snapshot.licenseNumber` 回填，进入待审/已通过状态后不直接编辑申请快照。

注意：**请求使用merchantName，快照使用name**。编辑回填时读取 `snapshot.name`，或以顶层 `merchantName` 为兜底。不要假设响应有storeName、place、history、submittedAt或任意未定义字段。

| state | 展示及下一步 |
|---|---|
| PENDING | 待审核，只查询；不开放员工经营权限 |
| REJECTED | 展示reason，允许修改资料并resubmit |
| APPROVED | 审核通过、待开通，展示营业码及网页开通指引 |
| CODE_EXPIRED | 展示营业码过期，可renewCode |
| ACTIVATED | 已开通，引导网页正常登录、建店；不再发码 |

营业码是 `MK-` 加32位十六进制字符，服务端生成大写，有效7天，仅成功开通一次。不是营业执照号、申请号、店员邀请码或登录密码。复制前宜刷新详情，避免复制已更新或已开通的旧码。

### 9.11 驳回后修改重提

`POST /app/merchant/onboarding/resubmit`

```json
{
  "onboardingToken":"手机号验证返回的凭证",
  "requestId":"onboard_20261027_resubmit_000001",
  "applicationNo":"原申请单号",
  "merchantName":"修改后的商家名称",
  "categoryId":11,
  "contactName":"联系人姓名",
  "introduction":"修改后的简介",
  "licenseNumber":"91350100123456789X"
}
```

字段与首次申请相同，增加必填applicationNo。只允许本人、已驳回且未开通的申请。成功后同一申请号、轮次递增、状态回到PENDING，旧轮次保留在服务端。

重提响应丢失时先info查询：已经PENDING或进入后续状态就按查询结果展示，不再重复重提；仍是REJECTED才允许重试原操作。不要将首次申请的requestId幂等规则误当成重提可无条件重复执行。

历史快照可能仍有旧address等字段，回填时仅取有效商家资料，禁止整体展开快照作为请求。旧地址不需要补填，不应成为重提必填字段。

### 9.12 重新获取营业码

`POST /app/merchant/onboarding/renewCode`

```json
{"onboardingToken":"手机号验证返回的凭证","applicationNo":"申请单号"}
```

仅本人审核通过且尚未开通申请可调用，返回更新后的详情和新营业码。旧码立即失效，重新计7天；不重复审批、不新建商家。

后端允许通过未开通的申请重新发码，并非仅CODE_EXPIRED能调用。前端通常只在过期或无法展示有效码时提供该操作；已有可用码时不要无提示反复轮换。

此操作不是使用requestId幂等：超时后先info，若已有新的有效码则使用它，不自动再次重发。已ACTIVATED时停止发码。

### 9.13 网页开通交接边界

移动端领取营业码后，引导申请人前往商家管理网页端：验证申请时同一手机号，获取网页自己的onboardingToken，再通过POST `/merchant/auth/activate`提交code、username、password一次开通OWNER。该接口由网页端实现，不在两个移动端增加账号密码、激活或建店表单；完整字段见独立接口文档第13节。

开通才创建正式商家和OWNER，不自动创建门店、不直接返回经营Token。开通后正常账号密码及图形验证码登录；OWNER在平台已授权范围内维护门店地址、坐标及人员。旧 `/merchant/auth/register` 已停用，新申请不得调用；旧密码重提只兼容历史申请。核销端使用已授权且绑定唯一门店的STORE账号，MANAGER/STAFF只作旧兼容标记；入驻通过不能代替staff/me身份校验及governance/me实际权限读取，详见第10章。

### 9.14 错误处理与旧接口迁移

| 情况 | 前端处理 |
|---|---|
| 手机号凭证过期/失效 | 清掉可展示码和临时凭证，验证原手机号后继续查询 |
| 图形码错误或失效 | 显示后端message，重新获取图形码 |
| 短信发送过频、验证码错误/过期 | 显示message，按限流重试；不提供前端固定万能码 |
| 申请不存在或无权访问 | 不显示其他申请数据；检查手机号及申请号，不切换为普通Token重试 |
| 旧requestId用于不同资料 | 查询原申请；未确认前禁止换资料复用 |
| 申请不处于已驳回 | 刷新详情，不强行重提 |
| 营业码过期/已更新 | 刷新本人详情，必要时显式重取最新码 |
| 已开通 | 转网页正常登录，不再发码或注册 |
| 网络结果未知 | 保留输入，按各操作的查询/重试规则处理，不伪造成功 |

旧 `POST /merchant/auth/register` 已停止接收新申请，返回业务码410和迁移提示（HTTP仍可能为200）。旧 `/merchant/auth/resubmit` 仅兼容历史账号密码申请，不用于新手机号申请；新前端统一调用本文 `/app/merchant/onboarding/resubmit`。

旧账号已有商家/门店/员工权限继续有效，不要求全部重新入驻。平台继续使用原审批中心；审核通过后的下一步是待开通，而不是直接开放经营。

### 9.15 用户端复用：前端操作注意事项

#### 一、前端需要增加什么

1. 在用户端合适位置提供“申请商家入驻”“查询入驻进度／领取营业码”入口。两者均允许游客使用，不能先要求注册或登录普通用户。
2. 申请页分两步：验证申请手机号 → 填商家名称、两级行业分类、联系人、选填简介 → 提交审核。
3. 进度页：验证原手机号 → 展示该手机号的多份申请 → 选择一份查看详情 → 按状态展示等待、驳回重提、营业码或已开通提示。
4. 审核通过后仅展示营业码，引导去商家管理网页端开通OWNER。用户端不新增经营账号密码、激活、建店或核销功能。

登录用户也允许申请；申请手机号可以由申请人自行验证，不应直接假定等于当前用户账号的绑定手机。申请归属始终由短信验证凭证确定。

#### 二、接口照用这一套，别换成普通用户认证接口

| 步骤 | 使用接口 |
|---|---|
| 图形验证码 | GET `/merchant/auth/captcha` |
| 行业分类 | GET `/merchant/auth/registrationCategories` |
| 发送短信 | POST `/app/merchant/onboarding/smsCode` |
| 验证短信 | POST `/app/merchant/onboarding/verify` |
| 首次申请 | POST `/app/merchant/onboarding/submit` |
| 申请列表 | POST `/app/merchant/onboarding/list` |
| 单份详情/领取码 | POST `/app/merchant/onboarding/info` |
| 驳回重提 | POST `/app/merchant/onboarding/resubmit` |
| 重新发码 | POST `/app/merchant/onboarding/renewCode` |

不要把这些步骤替换成普通用户注册、短信登录或绑定手机号接口。入驻验证不会创建普通用户，不应为了申请写入普通用户登录状态。

路径带 `/merchant` 不代表需要商家经营账号；路径带 `/app` 也不代表必须有APP用户Token。

#### 三、最重要：入驻凭证与用户登录态分开

- 上表9个请求均走公共请求通道，不附带已有普通用户或员工的 `Authorization`，也不触发普通用户Token刷新。
- 短信验证返回的 `onboardingToken` 放在独立入驻状态中，仅在后续JSON请求体传入；不要保存成普通用户 `token`，不要覆盖当前登录用户。
- 入驻凭证过期只清理入驻状态，引导验证原手机号继续查询；不能因此清空普通用户账号或跳到普通用户登录页。
- 普通用户退出登录、切换账号或业务请求401，也不要把另一种Token填入入驻请求。页面隐藏/切换手机号后，丢弃旧请求的迟到结果。
- 不将凭证、营业码或密码放进URL、控制台、埋点或持久存储。营业码仅本人详情展示，不缓存为可长期使用的登录资料。

接手时检查用户端实际网络封装：若它会自动带用户Token或强制登录，应增加明确的公共请求选项，或为入驻使用独立的请求适配器。**不能直接套用要求用户登录、自动加Authorization的交易请求函数。**

路由放行仅限新增的申请和查询页面；购券、券包、订单等原有鉴权规则保持。

#### 四、提交字段与分类选择

首次提交仅发送：

```json
{
  "onboardingToken":"短信验证返回的凭证",
  "requestId":"onboard_client_20261027_000001",
  "merchantName":"商家名称",
  "categoryId":11,
  "contactName":"联系人姓名",
  "introduction":"选填简介",
  "licenseNumber":"91350100123456789X"
}
```

其中分类ID是示例，必须来自实际分类接口。重提使用同样资料字段，再增加 `applicationNo`，调用resubmit。

- 商家名称最多100字、联系人最多50字、简介最多2000字；不要沿用核销端旧表单40字等旧限制。
- 新版申请/重提表单增加营业执照号，15或18位英文字母数字，提交前去首尾空格并转大写；请求白名单包含licenseNumber。后端保留旧端缺号兼容，不等于新版页面可以省掉此字段。
- 不收地址、地图位置、经纬度、首店、经营账号密码或营业执照上传。不另传手机号决定申请归属。
- 分类接口返回平铺数组；按parentId组织成两级，先一级行业再对应子类，显示名称路径，只提交二级categoryId。
- 不将一级、二级混排在同一个单列列表，不提交中文分类名称或路径数组。
- 驳回回填商家名称读取 `snapshot.name`，或以顶层 `merchantName` 兜底。分类按snapshot.categoryId恢复父子路径；执照号按snapshot.licenseNumber恢复，旧空值允许用户补填后重提。
- 历史快照可能带address；只取当前有效字段，不能将整个snapshot直接展开后重提。

#### 五、查询状态与营业码怎么展示

| state | 用户端操作 |
|---|---|
| PENDING | 显示待审核、刷新入口，不开放经营权限 |
| REJECTED | 展示reason，允许编辑并重提，保留applicationNo |
| APPROVED | 展示本人详情中的营业码、有效期和复制，引导网页开通 |
| CODE_EXPIRED | 提供重新获取营业码 |
| ACTIVATED | 显示已开通，去商家管理网页端正常登录；不再发码 |

只按 `state` 控制业务，不单凭reviewStatus=2就显示“账号已开通”。营业码不是普通用户优惠券码，不放入“我的券”，不生成可供消费核销的券或订单。

列表最多100条摘要，不返回可用营业码和完整驳回资料；领取码、看原因及修改前必须查info。详情仅当前轮次，不自行拼造完整审核历史。

营业码有效7天、成功使用一次；网页需验证申请时同一手机号，设置账号密码后一次开通OWNER。用户端不要调用 `/merchant/auth/activate`、旧 `/merchant/auth/register` 或旧密码重提入口。

#### 六、网络异常别重复申请

- 新申请生成一次requestId，连点防重；提交超时保留原资料和标识，查询或沿用原标识重试。
- 不确定是否受理时，不清空表单、换requestId再次申请。页面重启丢失临时标识时，先验证原手机号查询已有申请。
- 重提响应未知先查info；已经PENDING就表示已重提，不能再重提一次。
- 重发码前后均以info核实，已有新的有效码则不自动再次重发，避免使刚拿到的码失效。
- 凭证30分钟过期后重新验证原手机号继续处理；不要误当成要新建一个商家。
- JSON `code=1000` 才是成功；HTTP 200中的业务失败仍需显示message并保留可恢复的输入。

#### 七、复用核销端代码时的边界

可参考新仓库main提交0506a56中 `apps/merchant` 的入驻API、独立内存状态、共用资料表单、两级分类处理和状态展示。

不要整包覆盖用户端，也不要直接照搬核销端员工身份、测试经营账号、路由守卫、导航外壳、AppID或开发后端地址。复用协议和独立业务逻辑，按用户端现有组件风格接页面；复制带 `@/` 的模块时核对别名导入及依赖，确保没有暗中依赖merchant-auth或staff/me。

本次核销端推送仅包含 `apps/merchant`，根目录测试和独立文档未随该提交上传。需要参考测试时由本地交付，不能误以为远程一定已包含。

#### 八、交付前至少验证这些情况

1. 游客直接打开申请/查询，无需普通用户登录；不自动发送短信。
2. 已登录用户申请后，原用户Token、昵称、券包和购券功能不被清空或替换。
3. 两级行业切换正确，只发送二级ID；请求没有地址、首店、密码或旧Authorization。
4. 同一手机号查询多份申请，另一手机号不能看到原申请；凭证过期重新验证后仍能查询。
5. 待审、驳回重提、审核通过领取码、码过期重取、已开通五种状态均正确。
6. 超时重试不重复申请，换手机号/离开页面后旧响应不串入当前页面。
7. 微信小程序编译、输入框和分类选择、模拟器及真机可达后端分别检查；真实短信、提交申请等写操作使用约定测试资料。

核销端用户反馈跑通仅代表核销端已有验证结果，不能代替用户端接入后的验收。

## 10. 商家核销端认证与门店身份

文档核对日期：2026-10-30。登录/刷新路径保留，补门店账号类型、真实岗位、个人权限及数据范围。


本端使用账号类型accountType=STORE的已授权门店账号，每个账号绑定唯一门店。OWNER或其他MERCHANT类型账号属于商家管理范围，不能直接作为本端店员使用。岗位可以是店长、店员、财务或本店自定义岗位；MANAGER/STAFF保留为旧兼容标记，不代表完整权限。账号与岗位由有权上级在统一后台维护，不提供手机端员工邀请注册。

| 方法 | 路径 | 认证 | 请求 |
|---|---|---|---|
| GET | `/merchant/auth/captcha` | 无 | 无参数；返回captchaId、data图片，150×45 |
| POST | `/merchant/auth/login` | 无 | `{"username":"员工账号","password":"账号密码","captchaId":"图片ID","verifyCode":"图片字符","accountType":"STORE"}` |
| POST | `/merchant/auth/refreshToken` | 无 | `{"refreshToken":"刷新Token","accountType":"STORE"}` |
| GET | `/merchant/staff/me` | MERCHANT Token | 无参数；兼容门店身份与记录范围 |
| GET | `/merchant/governance/me` | MERCHANT Token | 无参数；真实岗位、数据范围、实际权限 |
| POST | `/merchant/governance/personal` | MERCHANT Token | `{"name":"新的显示姓名"}`；只改本人姓名 |
| POST | `/merchant/auth/changePassword` | MERCHANT Token | `{"oldPassword":"原密码","newPassword":"新密码"}` |
| POST | `/merchant/auth/logout` | MERCHANT Token | 无业务参数，可传 `{}` |

### 登录与刷新响应

成功data为 `{"token":"访问Token","expire":7200,"refreshToken":"刷新Token","refreshExpire":604800}`；有效时长单位秒，以实际响应为准，不能写死。成功登录后读取staff/me确认唯一门店，并读取governance/me取得真实岗位和permissions，再开放对应页面及操作。任一身份校验失败时不伪造权限或使用本地测试身份代替。accountType是新增可选字段，旧移动端不传仍兼容；新版建议明确传STORE。刷新请求沿用同一账号类型。

### 当前门店身份

staff/me的data仍为id、username、name、merchantId、merchantName、storeId、storeName、role、roleText、canViewStoreRecords，响应结构未删除旧字段。

- role/roleText仍是兼容用MANAGER/STAFF、店长/员工；显示自定义岗位时应取governance/me.roleName，不用旧roleText覆盖它。
- canViewStoreRecords反映是否允许本店范围；不可继续写成“MANAGER必为true、STAFF必为false”。它只表示数据范围，是否可以调用记录接口还须检查bill:view。
- 未绑定、多绑定、跨商家、账号/商家停用、门店禁用/关闭或岗位失效均拒绝；2停业允许合法身份查看历史，不允许核销。staff/me成功不代表门店正在营业，核销前仍以inspect及写接口校验为准。

### 实际岗位与权限（新增）

`GET /merchant/governance/me`。手机核销端仍携带MERCHANT Token；如带X-Workspace，值为STORE。下例中ID、名称仅作格式示例，数组按实际响应处理，不写死岗位名称或ID：

```json
{
  "code":1000,
  "message":"success",
  "data":{
    "id":901,"username":"13800000000","name":"示例员工",
    "accountType":"STORE","merchantId":10,"merchantName":"示例商家",
    "storeId":101,"storeName":"示例门店",
    "roleId":201,"roleName":"门店财务","storeScope":"STORE","storeIds":[101],
    "defaultStoreId":null,"owner":false,
    "permissions":["bill:view"],"menuIds":[301],"grantMenuIds":[]
  }
}
```

| 字段 | 含义及核销端处理 |
|---|---|
| accountType | 本端应为STORE；Token类型仍为MERCHANT |
| roleId / roleName | 唯一真实岗位；可以是自定义名称，不按“店长/财务”字符串判断权限 |
| storeId / storeName / storeIds | STORE账号唯一门店；storeIds只应包含绑定门店，不提供跨店切换来扩大范围 |
| storeScope | SELF仅本人记录；STORE本店记录，具体口径见12、13章 |
| permissions | 服务端已合并岗位、个人允许/禁止及上级功能上限后的实际权限；菜单和按钮按它显示 |
| menuIds / grantMenuIds | 网页目录及可下放配置标识；小程序不用它们自动生成网页路由，也不能自行增加权限 |
| defaultStoreId / owner | 统一模型兼容字段；门店账号不拿商家默认店替换自己的绑定门店 |

| 移动端能力 | 权限条件 |
|---|---|
| 验券inspect、纯试算preview | redeem:use |
| 开单prepare、改金额revise、确认confirm、内容券redeemContent、取消cancel | redeem:use，且写接口仍校验门店营业状态与券规则 |
| 消费账单page、核销流水page | bill:view；再按本人/本店数据范围过滤 |
| 消费账单info | bill:view或redeem:use，并满足该账单的数据归属；支持核销中的结果恢复 |

一个账号可以只有bill:view（如门店财务），也可以只有redeem:use，或两者都有；页面不能因为登录成功就把两个功能都开放。相同岗位的两个人也可能因个人增减权限而不同。上级收回功能后接口立即按新授权校验，403显示提示并刷新身份/权限，不反复刷新Token；账号已被停用等401按认证流程退出。返回页面或重新进入时刷新上下文，清除失去权限的旧页面数据。

governance/permmenu及岗位、账号、商家/门店授权管理接口主要供统一网页后台使用，本轮不要求在核销小程序新增员工/岗位管理页面。普通用户APP Token不能调用本节商家身份接口。

### 修改本人显示姓名（新增）

`POST /merchant/governance/personal`，请求 `{"name":"新的显示姓名"}`。name必填，去首尾空格后1～50字；成功data为空，重新读取身份刷新显示。不接收roleId、merchantId、storeId、storeScope等字段，不支持借此更换登录手机号/账号或自行提权。密码仍调用原changePassword。


### 会话与密码

刷新轮换会话；退出使访问和刷新令牌同时失效。账号停用、密码重置、角色/门店改变后旧会话失效。changePassword验证原密码，新密码6至64位且BCrypt输入不超过72字节，不能与原密码相同，成功data为空；修改成功后清理本地认证并重新登录。

只持久化认证凭证，不持久化门店私有记录；403不触发无限刷新。改密码与认证请求不记录明文密码、验证码或Token。

## 11. 验券识别与优惠试算

文档核对日期：2026-10-25；协议来源更新日期：2026-10-23；2026-10-24新增分流字段；2026-10-30复核验券权限及营业状态限制，请求与分流响应沿用原协议。


### 识别券

`POST /merchant/redemption/inspect`；具有redeem:use的STORE账号使用MERCHANT Token；请求 `{"code":"完整64位小写十六进制券码"}`。storeId可省略；传入必须等于当前绑定门店。扫码结果原样传，不把持券ID或购券订单号当券码。

识别只查询，不建账单、不核销、不预占资格；校验实际授权、账号、门店营业状态、归属、快照适用范围、顾客状态、有效期和持券状态。门店2停业、0禁用、3关闭不能用于核销；停业不等于券已作废，不由前端自行改券状态。失败展示message并阻止后续确认。

### 成功返回

沿用code=1000、message、data的统一包装。data包含：

| 字段 | 说明 |
|---|---|
| customerCouponId、couponName | 持券ID和发券时券名称 |
| merchantName、storeId、storeName | 商家与当前核销门店 |
| type、typeText | 类型编码、中文名称 |
| requiresConsumptionAmount | 是否需要先填写消费金额，再进行试算与确认 |
| description、validFrom、validTo | 持券使用说明及实际有效期 |
| minSpend | 消费门槛，整数分，无值可为null |
| contents | 套餐、兑换、体验项目及数量 |
| rule | 发券时公开规则快照，与顾客持券详情rule结构一致 |
| confirmed | 恒为false，不是核销成功 |

| type | typeText | requiresConsumptionAmount |
|---|---|---|
| FULL_REDUCTION | 满减券 | true |
| DISCOUNT | 折扣券 | true |
| CASH | 代金券 | true |
| PACKAGE | 套餐券 | false |
| EXPERIENCE | 体验券 | false |
| EXCHANGE | 兑换券 | false |

rule包含name、type、description、scopeType、storeIds/storeNames、contentItems、ruleVersion、allowCombine，以及salePrice、minSpend、discountAmount、deductAmount、maxDiscount、discountRate。

金额统一为整数分；discountRate为折数，例如8.8表示8.8折。rule.discountAmount是满减规则面额，并非本次实际优惠。

inspect不返回顶层discountAmount/consumptionAmount，避免把仅识别误当作已试算。本次优惠由prepare返回，独立试算时由preview返回。

### 分流字段与调用顺序

inspect额外返回nextAction：金额类为ENTER_BILL，内容类为CONFIRM_CONTENT。

- ENTER_BILL：输入金额/备注 → consumption/prepare → 核对账单号、优惠、补款 → 线下收款 → consumption/confirm。
- CONFIRM_CONTENT：核对套餐/体验/兑换内容 → consumption/redeemContent，自动开单并核销。

### 可选的纯试算

`POST /merchant/redemption/preview`，请求 `{"code":"完整券码","consumptionAmount":15000}`；storeId规则同inspect。金额类必须传正整数分，内容类允许省略金额。

返回customerCouponId、couponName、merchantName、storeId/storeName、type/typeText、requiresConsumptionAmount、nextAction、description、validFrom/validTo、minSpend、contents、consumptionAmount、discountAmount、confirmed=false。顶层discountAmount为本次计算优惠，不等于规则中的面额。

preview不核销、不建账单、不占券；新流程prepare已返回试算结果，可以省略这次调用。不要根据预检成功直接把券标记为已使用。

## 12. 消费账单与确认核销

文档核对日期：2026-10-25；协议来源更新日期：2026-10-24；2026-10-30复核操作权限与本人/本店数据范围，原账单请求及金额协议保持。

### 最终交互及范围

首页一个「扫码用券」入口，扫码一次即可：

- 满减 FULL_REDUCTION、折扣 DISCOUNT、代金 CASH：inspect → 弹框填写金额及备注 → prepare → 展示账单、优惠和补款 → 商家线下收款 → confirm。
- 套餐 PACKAGE、体验 EXPERIENCE、兑换 EXCHANGE：inspect → 展示券内容 → 点击确认使用 → redeemContent，一次事务完成建单及核销，无需补款。
- 扫码识别、试算、建立待结算账单均不消耗券。无需重新扫码。
- 差价第一版采用商家人工确认线下已收款，**不接真实支付、不调用微信扣款、不让顾客在用户端支付**。OFFLINE仅表示商家确认收到了款。
- 一笔消费账单一张具体持券，一张券只能有一个待结算或成功账单。取消释放占用，允许另建账单。
- 本版不处理套餐混合加购、多券叠加、退款、撤销已完成核销。内容券单独成单。

### 通用约定

- 商家接口沿用原始 `Authorization: token`，不加 Bearer；登录、刷新、验证码路径不变，新增可选accountType见第10章。写接口需redeem:use，page需bill:view，info需其中之一；不能只按MANAGER/STAFF开放按钮。
- 成功结构：`{"code":1000,"message":"success","data":...}`。失败按 `code != 1000` 处理并展示 message；认证失败也可能是 HTTP 401/403。
- 所有输入和输出金额均为**整数分**：150元传15000，禁止浮点金额。
- merchantId、operatorId、优惠金额、订单号、状态等由后端产生，不能由前端指定。
- 门店账号可省略 storeId，后端取绑定门店；显式传其他门店会拒绝。OWNER 操作建单须显式指定本商家门店。
- `requestId`：前端为每次新开单产生8～64位字母数字/下划线/短横线标识，例如 UUID。一次操作的超时重试继续使用原标识；下一单换新标识。
- 同一操作人、同一 requestId、相同内容返回原单，不会多开单；不能更换金额/券/门店/备注后复用。账单修改后以 info 查询原单，不再拿初始开单请求覆盖它。

### 新增商家接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/merchant/consumption/prepare` | 金额类券验门槛、试算并建立待结算账单 |
| POST | `/merchant/consumption/revise` | 修改待结算账单金额、备注，保留原账单号 |
| POST | `/merchant/consumption/confirm` | 确认收款、完成账单并核销 |
| POST | `/merchant/consumption/redeemContent` | 内容类券自动开单并核销 |
| POST | `/merchant/consumption/cancel` | 取消待结算账单、释放券 |
| POST | `/merchant/consumption/page` | 按身份查询消费账单 |
| GET | `/merchant/consumption/info?id=账单ID` | 查询消费账单详情及关联券、核销记录 |

#### prepare：金额类券开单

```json
{
  "storeId": 1,
  "code": "扫码获得的64位小写十六进制券码",
  "consumptionAmount": 15000,
  "remark": "3号桌",
  "requestId": "前端生成的UUID"
}
```

code、consumptionAmount、requestId必填；remark可省略，最多200字；消费金额须大于0，最多9999999999分。适用门店、有效期、顾客状态和门槛均在后端检查。

成功返回本章的OrderView：`status=PENDING`，`version=1`。示例满120减20的券对应 discountAmount=2000、payableAmount=13000。未达到门槛不创建账单、不核销，弹框保留用户输入。

券已关联其他待结算账单时不会重复建单；前端应引导查询原账单并继续结算或取消。待结算账单目前不会自动超时取消，需显式调用 cancel。

#### revise：在同一账单上修改金额

```json
{"orderId":123,"version":1,"consumptionAmount":16000,"remark":"3号桌，增加消费"}
```

orderId、version、consumptionAmount必填。只支持待结算金额类账单，重新验证券和门槛。成功后保留id/orderNo，version递增，返回新的优惠和应补款。remark省略会置为空串。

前端必须用最新返回的版本和金额刷新收款确认界面，不能继续提交旧金额。

#### confirm：商家确认线下已收款并核销

```json
{"orderId":123,"version":1,"receivedAmount":13000}
```

三个字段必填。receivedAmount必须严格等于账单payableAmount；无需补款传0。不得将顾客先前购买券的价格计入本次receivedAmount。

成功后：

- status=COMPLETED；有补款paymentMode=OFFLINE，无补款paymentMode=NONE。
- 账单完成、成功核销记录、券已使用在同一数据库事务提交。
- confirmedBy/confirmedByName记录最终确认人，operatorId/operatorName记录开单人。
- 相同订单、相同收款金额的完成确认可重试，返回原结果，不重复收款或核销；完成后的重试不要求version仍是最新值。
- 待结算时version不符、券过期/已作废/本店不适用、金额不符都会拒绝完成；保留待结算账单，可取消。错误后不要先清空页面。

**本接口只是人工收款确认，不执行资金支付。** 不能仅凭点击过收款按钮或前端页面切换就调用成功确认。

#### redeemContent：套餐/体验/兑换券一键完成

```json
{"storeId":1,"code":"扫码获得的券码","remark":"双人套餐","requestId":"前端生成的UUID"}
```

不传consumptionAmount；金额类券不能调用此接口跳过收款流程。

在同一事务内生成唯一账单号、保存发券时的商品/服务快照、核销并完成账单。响应：status=COMPLETED，consumptionAmount=null，discountAmount=0，payableAmount=0，receivedAmount=0，paymentMode=NONE，redemptionId有值。

这里的0表示「本次无需补款」，不表示顾客买券免费。购券价在couponSnapshot.salePrice，购券交易仍保留在purchase_order。商品/服务及数量从couponSnapshot.contentItems读取。

#### cancel：取消账单

```json
{"orderId":123}
```

只支持PENDING → CANCELLED。返回原账单，不删除历史；券不核销并释放占用。重复取消返回同一结果。已完成账单不允许取消。

修改待结算金额优先使用revise，保持原单号；取消后重新开单须更换requestId，生成新单号。

#### page：分页查询

```json
{"page":1,"size":20,"storeId":1,"status":"COMPLETED","orderNo":"XF...","customerCouponId":456}
```

所有筛选可省略。page默认1、范围1～100000；size默认20、范围1～100。orderNo精确匹配；customerCouponId用于从一张持券反查关联账单。按账单ID倒序。

```json
{"list":[],"pagination":{"page":1,"size":20,"total":0}}
```

身份过滤由后端强制执行，消费账单page不传scope，传了也不能改变后端授权：

- STORE账号且storeScope=SELF：仅绑定门店、本人开出的账单。详情、修改、取消、确认也受此数据范围限制；写操作另需redeem:use。
- STORE账号且storeScope=STORE：绑定门店全部账单；只有同时具备redeem:use才能处理其中待结算账单。只有bill:view的财务账号仅查询。
- 历史账号尚无storeScope时保留旧STAFF本人、MANAGER本店的兼容；新版前端不把该兼容默认写成永久规则。
- 商家网页账号按本商家ALL/SELECTED门店范围过滤，不是手机门店账号的跨店授权入口。
- 伪造storeId、merchantId或客户端scope不能扩大范围。门店停业可查看合法历史，不能继续消费开单/核销；恢复或改岗后重新读取真实权限。

#### OrderView字段（开单、修改、确认、取消、详情和列表统一）

| 字段 | 含义 |
|---|---|
| id / orderNo | 内部账单ID / 后端生成的全局唯一账单号；修改、结算、重试均保留原号 |
| merchantId / merchantName | 所属商家及开单时名称快照 |
| storeId / storeName | 所属门店及开单时名称快照 |
| operatorId / operatorName | 开单人ID及名称快照 |
| confirmedBy / confirmedByName | 完成核销的确认人ID及名称快照，未完成为空 |
| customerCouponId | 顾客具体持券ID，不能用券模板ID替代 |
| couponName / couponType | 用券名称及六种券类型 |
| couponSnapshot | 发券时规则的公开快照；金额为分，包含套餐明细等；不包含原始券码 |
| status / statusText | PENDING/待结算、COMPLETED/已完成、CANCELLED/已取消 |
| consumptionAmount | 到店消费金额，整数分；内容类为null |
| discountAmount | 本次金额优惠，整数分；内容类兑换不折算为优惠金额，为0 |
| payableAmount | 本次还需补款，整数分 |

## 13. 核销记录

文档核对日期：2026-10-25；协议来源更新日期：2026-10-22；2026-10-24增加账单关联；2026-10-30复核bill:view权限及scope自动选择规则。


`POST /merchant/redemption/page`，MERCHANT Token。

请求：`{"page":1,"size":20,"scope":"self"}`；storeId可选，但门店账号只能传绑定门店。page默认1，size默认20、上限100。成功data为list/pagination标准业务分页。

本接口需要bill:view；根据真实数据范围自动选择scope，不再根据岗位名称或MANAGER/STAFF写死：

| 已授权的数据范围 | 前端自动选择scope | 后端范围 |
|---|---|---|
| governance/me.storeScope=SELF | self | 当前绑定门店且本人完成的核销 |
| governance/me.storeScope=STORE | store | 当前绑定门店全部核销 |

不展示越权范围切换按钮。兼容尚未读取新上下文的旧客户端时，至少用staff/me.canViewStoreRecords选择true→store、false→self，而不是用role字符串。该布尔值不代替bill:view检查；权限可能已被上级收回。

旧流水接口省略scope时，门店账号（包括店长）仍默认self；要查看已授权本店流水须显式传store。SELF账号伪造store会被拒绝。消费账单page则直接按后端授权自动过滤，不接受scope作为范围选择。

记录字段：id、customerCouponId、couponName、storeId、storeName、operatorId、operatorName、consumptionAmount、discountAmount、redeemedAt、consumptionOrderId、orderNo。金额整数分；不返回原始券码和顾客手机号。历史记录的consumptionOrderId/orderNo可能为null，不补造订单号。

当前PageInput只接收page、size、storeId、scope，**没有关键词、日期、券类型筛选，也没有独立流水详情路由**。不要把未支持条件当成已过滤结果。按消费账单号精确搜索请用consumption/page的orderNo，详情用consumption/info。

## 14. 旧接口兼容、能力缺口及联调顺序

### 必须同步的破坏性变更

`POST /merchant/redemption/confirm` 仍存在，但已是消费账单确认的同义入口。请求改为 `{"orderId":123,"version":1,"receivedAmount":13000}`，响应是OrderView；不能再提交 `{storeId,code,consumptionAmount}`。新接入统一使用consumption/confirm，以status=COMPLETED判断成功，不依赖旧confirmed字段。

### 本汇总不提供的业务

- 员工邀请、邀请码注册/加入门店、撤销邀请没有已确认接口，不开发假流程。
- 核销记录关键词/日期/类型搜索尚未在当前DTO接收；账单号搜索可用消费账单接口。
- 当前消费账单必须关联持券，不提供普通无券消费开单或顾客端消费单在线支付。
- 不接真实支付、多券叠加、分次核销、套餐混合加购、退款或撤销已完成核销。
- 顾客持券已使用状态可查；独立的本人消费账单/核销历史接口尚未发现，不调用商家接口代替。
- 本轮不要求在核销小程序新增建券、审核、统计、反馈、员工或岗位管理页面。统一后台已有账号/岗位/逐级授权接口，网页接入见[三端统一后台接口](三端统一后台接口-20261030.md)；本汇总只补移动端需要的身份、有效权限和个人姓名维护。不能把网页viewPath当小程序页面路由。

### 联调前提和顺序

1. 后端部署需包含最新消费账单、门店定位、入驻激活增量；仅旧版本重启不等于升级成功。已执行数据库不可清空重建。
2. 用户：验证码/登录 → person/account → 分类/门店/券浏览 → create+simulatePay或claim → wallet → 展示后端二维码。
3. 门店账号：captcha/login（可选accountType=STORE）→ staff/me + governance/me → 按redeem:use或bill:view开放能力 → inspect及原金额券/内容券流程；流水scope按真实数据范围选择。
4. 核销成功后刷新用户券包，确认USED；验证重复提交不重复开单/核销，取消待账单不消耗券。
5. 不让测试用例消耗真实演示券，真机摄像头、二维码、短信送达和微信身份兑换必须另做实际验收。

### 维护规则

本文件作为两个移动端的统一交接入口；原模块文档保留历史依据。接口变化须更新对应业务章节和顶部日期/更新记录，明确参数、权限、响应是否破坏兼容。每个模块的核对日期不代表该模块接口都在当天新增。

### 18.4 平台虚拟储值卡与支付

一位顾客一个平台虚拟余额账户；没有实体卡号、转赠、提现、退款、赠送余额或自动过期扣减。1元充值=1元余额。所有正常商家下的正常营业门店可参与直接消费；购券须选择原券适用门店。服务端余额/流水为唯一事实，不在移动端本地模拟。

| 方法 | 路径 | 请求/返回 |
| --- | --- | --- |
| GET | /app/wallet/balance | data为余额整数分，无账户时0 |
| POST | /app/wallet/recharge | requestId、amount、result可省略SUCCESS或FAILED；返回流水 |
| GET | /app/wallet/bill?billNo=W... | 根据门店提供的随机账单编号读取待付无券账单 |
| POST | /app/wallet/quote | billNo或purchaseOrderId+storeId，返回服务端活动应付试算 |
| POST | /app/wallet/pay | requestId、与试算相同目标、expectedAmount；返回支付流水 |
| GET | /app/wallet/transactions | pageNumber、pageSize；本人充值/消费/购券流水 |
| GET | /app/wallet/activities?storeId=51 | 可省storeId；当前已发布且在时间内的活动数组 |

充值示例：`{"requestId":"recharge_20261102_01","amount":10000,"result":"SUCCESS"}`。单笔1至100000000分，演示余额上限1000000000分。FAILED保存失败流水且amount=0、不入余额；同请求改金额/结果返回409。并发充值、扣款按顾客及余额行锁串行处理，不允许透支。

**无券直接消费**：门店工作人员在管理网页或核销端开具账单，顾客读取随机billNo，展示merchantName、storeName、amount、remark及状态后再试算；顾客不能自行传消费金额开单。此账单独立于原优惠券核销消费账单，不能对原核销单重复收款。状态PENDING待支付、PAID已支付、CANCELLED已取消；已支付账单暂不支持取消/退款。billNo是随机不可枚举的支付邀请编号，只交给付款顾客，不公开发布。

试算请求：

```json
{"billNo":"W0123456789abcdef0123456789abcdef"}
```

购券试算请求：`{"purchaseOrderId":201,"storeId":51}`，先使用原/app/order/create创建待支付购券订单。storeId须属于订单商家且适用于原优惠券，用该门店匹配支付活动；支付活动不改变原优惠券自身的核销范围。免费券继续原claim流程，不走余额扣款。

试算返回：

```json
{"originalAmount":10000,"amount":9000,"discountAmount":1000,"activityId":31,"activityTitle":"九折活动","discountRate":9}
```

未命中时activityId/activityTitle为空、discountRate=10、amount=originalAmount。折扣9表示九折，按分四舍五入，应付最低1分；同笔只取优惠最大的一个活动，不叠加，同额时优先较新活动。活动适用于直接消费原额或购券售价，不对充值打折。

确认支付：

```json
{"requestId":"wallet_pay_20261102_01","billNo":"W0123456789abcdef0123456789abcdef","expectedAmount":9000}
```

购券支付：`{"requestId":"wallet_coupon_20261102_01","purchaseOrderId":201,"storeId":51,"expectedAmount":900}`。两种目标互斥。expectedAmount必须是用户最后确认的试算应付金额，服务端会重新匹配活动；金额变化/未确认返回409，不静默多扣。余额不足、门店失效、订单过期或规则变化均不扣款、不发券。购券扣款与既有库存/限购/发券处于同一事务，不再调用原simulatePay作为第二次支付；原已支付订单不能再扣储值。

请求超时沿用同一requestId及完整参数重试；相同已成功交易返回原流水，不重复扣款/发券。确认收到金额变化409后可重新试算、重新确认尚未成功的请求；成功流水的内容不能更改。同一个已支付账单/购券订单更换requestId也不能再次扣款。

流水字段：id、requestId、type（RECHARGE模拟充值/DIRECT直接消费/PURCHASE购券）、status（SUCCESS/FAILED）、customerName、merchantName、storeName、originalAmount、amount、discountAmount、activityTitle、discountRate、balanceAfter、purchaseOrderId、billId、createTime。amount均为正数；根据type判断入账或支出，FAILED不产生资金变化。原购券订单totalAmount仍为原售价总额，本次实扣和活动优惠以储值流水为准，不能把原额当作本次实付。

### 18.6 工作人员站内通知

2026-11-09增量：[完整轻通知与强提醒协议](../api-docs/通知轻通知与强提醒-20261109.md)。发送新增 `noticeType:LIGHT|STRONG`（省略为LIGHT）；列表/详情新增noticeType、confirmedAt，回执新增confirmedAt。`GET /pending?pageNumber=1&pageSize=20`按通知ID升序返回本人未确认STRONG分页；`POST /confirm {"id":通知ID}`幂等确认并同时已读，data为更新后的通知详情。只读不确认，旧客户端能读通知但不会弹强提醒。核销移动端需接入队列弹窗，顾客APP仍无工作人员通知入口。

普通顾客无此模块入口。核销端使用 `/merchant/governance/notices`：

| 方法 | 后缀 | 说明 |
| --- | --- | --- |
| GET | /page?sent=false&pageNumber=1&pageSize=20 | 本人收件箱；sent=true仅本人已发送 |
| GET | /detail?id=通知ID | 本人收到的通知，不自动标已读 |
| POST | /read | {"id":通知ID}，只标本人阅读状态，重复保持首次时间 |
| GET | /unread | data为本人未读数 |
| GET | /recipients?pageNumber=1&pageSize=20 | 有发送权时取得具体可通知人员 |
| POST | /send | requestId、title<=100字、content<=5000字、recipientIds 1至100项 |
| GET | /receipts?id=通知ID | 仅本人发送的通知接收名单及readAt |

通知列表/详情：id、title、content、senderName、createTime、readAt；readAt=null为未读。收件箱、未读数、阅读状态不需要发送权；账号、商家、岗位须有效。发送仅上级管理岗位且实时持有notice:send；普通店员即使误配该权也不能发送。店长/自定义管理岗不能向同级管理岗、上级或其他店发通知；普通员工包括内置店员及未获发送权的自定义普通岗位。选择具体人员，不自动广播。无附件、短信、撤回或删除。

发送超时沿用原请求标识和内容；接收人非法整批拒绝，阅读/回执按账号隔离。更完整权限和运营接口见[站内下级通知接口](站内下级通知接口-20261102.md)。

### 18.7 移动端接手验收

- APP用户能提交反馈及图片，只能查自己的结果；平台回复后能看到单次结果。
- 顾客与同店两名员工互发文字/图片，重试无重复；跨用户/跨店拒绝；断网恢复按消息游标补拉。
- 模拟充值成功/失败、余额不足、支付试算过期后金额变化、成功请求重试及其他用户抢付已支付账单均覆盖。
- 购券储值支付后仍在原券包出现且只发一次；免费领券保持原流程。不要在余额支付后再次调用simulatePay。
- 活动仅在审核发布、生效时间及正常门店范围内展示；多活动最大单项优惠，前端不自行计算最终实扣。
- 核销端按真实redeem:use/bill:view和SELF范围显示操作；通知读写隔离，普通员工只收不发。
- 前端负责真实微信上传、会话恢复、支付确认交互与真机网络验收。本轮没有修改两个移动端代码，也未宣称真机或真实资金支付通过。

## 19. 统一消费结算（2026-11-05）

普通消费先由工作人员开单得到随机 `billNo`，随后选择金额类券或直接付款。付款顾客选择普通模拟支付或储值支付。消费 100 元、券优惠 20 元、储值九折时，实付 72 元。储值活动按最大单项优惠，时间区间为北京时间生效起止时间，开始包含、结束不含。充值按原金额入账。

### 商家与门店

前缀 `/merchant/governance/wallet`，沿用商家登录及 `X-Workspace`。开单、选券、取消和旧账单转入需要 `redeem:use`，查询需要 `bill:view`。门店范围及 SELF 本人账单限制均生效。

| 方法 | 后缀 | 参数 |
| --- | --- | --- |
| POST | /bills/create | 原接口，requestId、storeId、amount（整数分）、remark |
| POST | /bills/coupon | id（开单 ID）、version（初始 1）、code（金额券券码） |
| POST | /bills/import | orderId（旧 consumption_order 的 ID） |
| GET | /bills/info | id |
| GET | /bills/page | pageNumber、pageSize |
| POST | /bills/cancel | id |

选券会校验门店、券有效期、门槛和持券人，并关联原有待结算用券订单，预留该券。同一张券重复请求返回同一关联；需要换券时取消原单后重新开单。券属于哪个顾客，账单就限定由该顾客付款。直接付款的账单由首次成功付款的顾客取得。套餐、体验等内容券继续通过原扫码确认接口同事务自动建单核销。

账单新增 version、consumptionOrderId、couponDiscount、remainingAmount、paymentMode、paidAmount、settlementSnapshot。amount 是原消费额；remainingAmount 是券后余额；paidAmount 是最终实付。settlementSnapshot 保存券规则、活动、折扣、原额、券优惠和实付计算快照。WALLET 为储值，SIMULATED 为普通模拟支付。

### 顾客付款

前缀 `/app/wallet`，使用顾客令牌。

| 方法 | 后缀 | 参数 |
| --- | --- | --- |
| GET | /bill | billNo，原接口 |
| POST | /consumption/quote | billNo、paymentMode |
| POST | /consumption/pay | billNo、paymentMode、requestId、expectedAmount（整数分）、result 可省略或 SUCCESS/FAILED |
| GET | /consumption/page | pageNumber、pageSize，顾客自己的统一账单 |

试算返回 billNo、version、originalAmount、couponDiscount、remainingAmount、paymentMode、payment。其中 payment.amount 为需要顾客确认的实付，payment.discountAmount 仅为储值活动优惠，payment.originalAmount 为券后剩余金额。

付款成功 data 返回完整已支付账单。模拟失败保留待付款状态，券保持未核销，余额不扣款。余额不足时可充值后重试，或整笔选择 SIMULATED。零差额也需要提交确认以核销券。付款时服务端重新计算券和活动，expectedAmount 不一致返回业务码 409，前端须重新试算并让顾客确认。失败后使用原 requestId 重试时须保持目标及内容一致；切换付款方式属于新的确认请求。成功请求的相同重试返回原结果，其他请求不能再次支付同一单。

储值付款可继续使用原 `/quote` 和 `/pay`，现在支持已选券账单。原购券模拟支付和储值购券流程继续使用原接口。储值流水的 originalAmount 表示活动折扣前金额，即用券后的剩余金额；消费总额与券优惠见关联账单。普通模拟消费记录在账单中。

### 运营折扣

`POST /admin/wallet/activities/schedule` 需要 `activity:manage`。提交 id、enabled、startAt、endAt，日期使用 `yyyy-MM-dd HH:mm:ss`。运营可暂停或重新启用已发布活动，并调整时间。旧活动 enabled 为空按启用解释。每个活动独立控制，仍有其他生效活动时继续选其中最大优惠；全部暂停或没有活动处于时间区间时，储值按券后剩余金额扣款。历史已完成账单保留原快照。

管理端「支付优惠活动」的已发布记录有「启停与时间」入口。「储值消费账单」页面提供开单、选券、账单编号和刷新付款结果。金额类验券引导至该页面，旧待结算账单可点「转为顾客确认付款」。付款由顾客端完成。

### 历史兼容与部署

历史已完成的用券账单、内容券快捷核销以及旧储值流水按原记录查询。旧 PENDING 金额券单可通过 /bills/import 原子关联到统一账单，同一个旧单只产生一个关联，关联后原 confirm、revise、cancel 入口会提示使用统一账单，防止重复核销。取消统一单会同步释放用券预留。

旧无券 wallet_bill 的空 version 按 1、空券优惠按 0、券后金额按原额读取；旧 PAID 账单从原储值交易恢复实付显示。开发环境 AutoTable 升级，关闭自动改表的环境在启动前执行 [MySQL 增量](../docs/sql/unified-consumption-settlement-20261105.sql)。

成功 code=1000，未登录 401，身份或范围拒绝 403，价格或状态冲突 409；余额不足及券规则无效沿用项目业务错误 message。两个移动端按本文接入并自行完成页面及真机验收。

## 20. 活动参与与自动站内通知（2026-11-05）

接续总文档第19章的统一消费结算。平台活动范围内默认参与，商家可退出或排除授权范围内门店。退出、恢复、启停和时间变化在支付确认时重新计算，金额变化返回409，由顾客重新确认。券优惠加一个最大单项储值折扣的顺序沿用第19章。

### 权限与可见范围

活动申请沿用 `activity:apply`。新增 `activity:participate`（调整本商家参与）及 `activity:recipients:manage`（配置额外活动负责人），由上级在商家功能上限和岗位或个人权限中明确授权。参与及负责人配置使用 MERCHANT 身份；门店工作人员可读取本店通知关联的活动详情。

商家活动列表现在包含本商家申请，以及涉及自己授权门店的平台活动。平台活动中的门店信息在商家响应中只返回其授权范围。活动记录新增 `activityVersion`、`platformActivity`，支付快照也保存命中的活动版本。新发布活动固定发布时的正常门店和商家归属，详情中的门店列表以当前归属和有效状态过滤。

### 参与接口

前缀 `/merchant/governance/wallet/activities`，使用商家/门店令牌及 `X-Workspace`。

| 方法 | 后缀 | 字段与响应 |
| --- | --- | --- |
| GET | /detail | id；返回本人当前门店范围内的活动详情，登录后按范围校验 |
| GET | /participation | id；需activity:participate，返回id、version、exited、canExit、stores、excludedStoreIds |
| POST | /participation | id、version、excludedStoreIds，以及可选exited；返回更新后参与设置 |

stores为允许调整的门店，元素含id、name、merchantId。excludedStoreIds替换当前可见门店内的排除项，保留当前授权范围外原有配置。超范围ID返回403。version必须与当前活动版本一致，否则409并要求刷新。参与变更成功会增加活动版本并生成范围调整通知，重复提交相同设置不产生新版本。

canExit=true才可改变整商家退出状态。权限只覆盖部分适用门店时，传exited不得改变商家整体状态，可仅调整自己的门店。全部退出和恢复都要求对本商家全部适用门店拥有授权。已到期或已下架活动不接受参与变更。

### 额外活动负责人

以下后缀同时支持上述商家前缀及运营 `/admin/wallet/activities` 前缀。运营需activity:manage，商家需activity:recipients:manage。运营传merchantId，商家的merchantId可省略，传入时必须为本人商家。storeId为0或省略表示商家级，为门店ID表示门店级。

| 方法 | 后缀 | 字段与响应 |
| --- | --- | --- |
| GET | /contacts/stores | merchantId可选；返回可配置的门店id、merchantId、name |
| GET | /contacts/options | merchantId、storeId；返回可选账号id、name、roleName |
| GET | /contacts | merchantId、storeId；返回已配置额外接收账号ID数组 |
| POST | /contacts | merchantId、storeId、recipientIds（最多100）；替换该范围的额外接收人 |

商家级配置要求全部自家门店授权，门店级配置要求该门店授权。配置时验证账号当前归属、身份、岗位和启用状态；投递时再次校验。商家级额外负责人只收到其自身可访问门店有关的通知。失效账号配置可保留历史显示，但不能新保存为有效接收人。

所有有效商家老板和涉及门店的有效店长自动必收，不依赖额外名单，不能通过清空额外名单取消。普通店员仅在被有权上级明确配置时接收。必收账号缺失会记录缺岗提示，系统不会创建或提权账号。

### 运营发送记录及回执

仅运营前缀 `/admin/wallet/activities`，需activity:manage。

| 方法 | 后缀 | 参数与响应 |
| --- | --- | --- |
| GET | /notice-events | id为活动ID；返回事件数组 |
| GET | /notice-events/receipts | eventId；返回账号投递状态及独立readAt |
| POST | /notice-events/retry | id为事件ID；安排失败任务重试 |

事件含id、activityId、activityVersion、kind、dueAt、status、attempts、nextAttemptAt、gaps、lastError及不可变payload。kind为PUBLISHED、REMINDER、CHANGED、PARTICIPATION、CLOSED（提前结束）、ENDED（到期）。status为PENDING（等待计划或重试）、READY（投递中）、DONE、SKIPPED。账号任务status为PENDING、FAILED、SENT、SKIPPED；noticeId和readAt可空。

重试仅作用于失败或待重试任务，已投递任务不会重复发。未来计划任务不会因为点击重试而提前发送。失效、转移商家或转店的收件账号会跳过，不重新路由到别的账号。

### 通知与调度

沿用站内通知收件箱、未读数、详情和已读接口。新增businessType=WALLET_ACTIVITY、businessId、businessVersion、detailPath和actionPath。网页入口为 `/my/activities?id=活动ID`，会重新验证本人当前门店范围；移动端按businessId路由至自己的活动详情和参与设置。

通知正文包含活动名称、规则、折扣、生效时间和该收件账号授权范围内的门店。每个账号独立保存noticeId及已读状态。自动发送方为“平台活动通知”，手动通知仍受原有向下级发送规则约束。

活动发布事务只写持久化事件，不在发布事务中发送。待审和驳回不会生成发布通知。事件按活动ID＋版本＋种类唯一，投递按事件ID＋账号唯一，站内通知再次按事件＋账号幂等。每个账号通知与SENT状态同事务提交，失败单独记录并等待重试。通知故障不回滚已经成功发布的活动。

复用项目ScheduleConfig中已启用的Spring调度，默认启动5秒后运行、每30秒扫描，每轮最多30个事件和100个投递。失败按次数延后1至60分钟重试。可用 `perkly.activity-notifications.scheduler-enabled=false` 关闭扫描，用于独立测试或维护。Quartz启停不控制此扫描；服务恢复后持久化任务继续处理。

### 本次边界决策

- 新发布活动固定发布当时适用门店及商家归属，之后新开门店或迁入其他商家的门店不自动加入该版本。旧活动范围在下一次重要调整时固定，不补发历史发布通知。
- 同店有多名有效店长时全部必收；内置店长岗位或历史MANAGER身份按有效岗位和门店绑定判定。自定义其他活动负责人由上级显式配置。缺少老板或店长只记录缺岗提示。
- 每个活动版本安排一次开始前提醒。提前量最多24小时；不足24小时发布时，安排在发布至开始时间的中点。已开始活动不补发开始前提醒。重要变更产生新版本和新计划，旧版本未发出的提醒、到期任务跳过。
- 标题、折扣及平台适用范围仍通过原有下架重提流程调整。已允许的启停、生效时间和商家参与调整增加版本，保留旧事件快照和已完成交易快照。
- 额外接收人配置生效于尚未展开的事件，已保存的账号投递任务按当前归属再次校验。无接收人但有缺岗提示的事件视为已处理，后续新版本或提醒重新解析有效账号。

开发环境AutoTable扩展表结构；关闭自动改表的环境先执行统一结算增量，再执行 [活动参与与通知MySQL增量](../docs/sql/activity-participation-notices-20261105.sql)。两个移动端按本文接入活动详情、参与设置和通知路由并自行完成真机联调。

## 21. 跨商家消费集章

更新：2026-11-06。后端 cool-admin-java-test；统一网页 cool-admin-vue-8.x。两个移动端仅交接口，不修改页面源码。

### 管理端操作

入口「跨商家消费集章」，路由 /workspace-admin/stamps。运营须具备 stamp:manage；旧角色不自动加权。后端重新启动注册菜单，管理端部署本次构建后重新登录。本文不表示已部署到现有 Docker。

1. 新建集章活动：填写名称、说明、北京时间起止时间，选择2至20个不同商家，为每个商家选择参与门店。门店不选则保存时展开该商家当时的全部正常门店；发布时再次校验，之后新店不自动加入。
2. 选择任务专用奖励券。没有时点「制作奖励券」：选择所属商家、现有六种券类型、使用规则、适用门店、库存、每人上限和有效期，保存提交审核。原公开券不能直接切换任务渠道。
3. 奖励券须审核通过并上架。制作和审核额外要求原 coupon:template:add / coupon:template:update 权限。制作调用原模板、内容、有效期和审核流程，不跳过审核。
4. 保存草稿后在列表发布，确认摘要中的商家、奖励及库存。发布后商家目标、门店、奖励模板和奖励规则版本固定。每人每个活动只奖励一次。
5. 「启停与时间」调整后续消费；「下架」停止新增集章。已赚到的章及已达标待发奖励保留。
6. 「进度与奖励」查看顾客、已集商家、章数、奖励状态和失败原因；「发放记录」查看尝试记录。库存不足时补库存，再点「重试发奖」。
7. 「补库存」同事务增加活动奖励额度及有限量任务券模板的库存，记录操作人和请求标识。只补容量，优惠规则版本保持不变。若奖励券失效、下架、规则版本变化或达到每人上限，先处理相应原因；不会绕过原券规则。
8. 「通知回执」复用站内通知，查看发布、提醒、变更及结束投递。商家仍通过原活动参与入口按授权范围退出或排除门店；已完成进度保留。

### 已确定规则与实施决策

- 一家商家一章，同商家多门店或多次消费不重复；必须完成全部指定商家。
- 只统计部署后正常流程产生的已完成到店消费。购券不计；待支付、取消、失败不计。套餐、体验、兑换等内容券完成且补款为0也计。
- 用券消费按持券人归属，无券账单按实际付款人归属；客户端没有上传消费凭据或认领他人订单的接口。
- 统一账单关联用券消费只生成一条规范消费来源，避免两套账单重复计章。
- 消费完成事务保存唯一来源及当时命中的活动版本。暂停、退出、到期后不追溯撤销已赚取的章，也不补计发布前的历史消费。
- 进度处理与发券分别提交事务。发券失败不会回滚已支付订单或丢失进度；默认每10秒扫描，失败按次数退避，最多1小时。运营可手动重试。
- 原券模板库存、每人上限、审核发布状态和冻结版本仍生效，另有活动库存额度。达标后即使活动结束也会继续重试发奖。
- 券渠道 PUBLIC（历史NULL同PUBLIC）和 TASK_ONLY 创建后不能切换。任务券不出现在公开发现列表，不能通过公开领取或购买接口绕过任务。达标券 sourceType=TASK_REWARD，进入原券包和核销流程。
- 活动类型 STAMP 复用通用标题、时段、版本、门店范围、参与及通知。DISCOUNT（历史NULL）独立用于储值折扣报价，集章不参与支付折扣计算。
- 无退款、提现、余额奖励或循环集章。各活动独立计章，不额外叠加发放同一活动的奖励。

### 通用契约

标准响应 {code:1000,data:...,message:...}；错误沿用框架，业务版本冲突409。认证沿用各端现有 Authorization。分页 pageNumber 默认1、pageSize默认20（1至100），返回 {list,total,pageNumber,pageSize}。

日期字符串 yyyy-MM-dd HH:mm:ss，北京时间，结束时间不含。金额型奖励券复用原 CouponTemplateEntity 的**元**制小数，不能误按支付接口的分制传入；本集章活动自身没有消费金额门槛字段。

## 22. 用户端 AI 聊天（2026-11-10 核对补齐）

本章以当前后端 Controller、UserAssistantModels、UserAssistantService 为准。接口已实现不代表手机页面已接入或当前服务器已部署。此助手只读；与管理网页的优惠券创建/修改助手、顾客与门店人工聊天是不同功能。

### 22.1 身份与请求

使用有效 APP 用户 Authorization，游客、商家、运营令牌不能代用。用户身份由服务端读取，禁止传 userId/customerId 指定查询他人资料。普通 JSON 请求与 R 响应，无 SSE 流式协议。

`POST /app/ai/assistant/chat`

首次仅传 message；后续沿用返回的 sessionId，不需要自行拼接历史消息：

```json
{"message":"帮我找福州20元以内的咖啡券"}
```

```json
{"sessionId":"服务器返回的会话ID","message":"只看免费的","location":{"longitude":119.30,"latitude":26.08}}
```

| 字段 | 约束 |
|---|---|
| message | 必填，1～1500字 |
| sessionId | 首次省略，后续用服务端返回值 |
| location | 可选，真实 GCJ-02 longitude/latitude，不猜测坐标 |
| target | 可选，形如 {"kind":"WALLET","id":123}；kind 为 COUPON/STORE/WALLET/ORDER；ID为正数并重新校验归属 |

COUPON 的 ID 为券模板 ID，WALLET 为本人持券 ID，ORDER 为本人购券订单 ID。规则解释支持 COUPON/WALLET。不能把消费账单 ID 传作购券订单 ID。

### 22.2 响应与展示

以下为结构示例，ID和内容不代表真实数据：

```json
{
  "code":1000,"message":"success",
  "data":{
    "sessionId":"服务器返回的会话ID",
    "message":"找到了符合条件的券，可以点开查看。",
    "cards":[{
      "kind":"COUPON","id":123,"title":"咖啡代金券","merchantName":"示例咖啡店",
      "cover":"/upload/example.jpg","statusText":"可领购","priceCents":0,
      "purchasable":true,"destination":"COUPON_DETAIL",
      "facts":[{"label":"购券价格","value":"免费领取"}]
    }],
    "suggestions":["推荐便宜的券","看看我的券","查看我的订单"],
    "conditions":{"area":"福州","keyword":"咖啡","priceMode":"FREE","maxPriceCents":2000,"spendBudgetCents":null,"cheap":false,"nearby":false},
    "degraded":false,"partial":false
  }
}
```

cards 固定为数组；facts 为 label/value 展示数组；suggestions 为可点击的下一句建议。conditions 是服务端保留的查询条件，priceMode 为 ANY/FREE/PAID。priceCents、maxPriceCents、spendBudgetCents 单位均为分；0表示免费，null才表示未知。消费预算用于门槛过滤，不等同最终应付金额；ORDER 卡片 priceCents 为订单总金额。

| destination | 卡片 id 的含义 | 手机页面 |
|---|---|---|
| STORE_DETAIL | 门店ID | 门店详情 |
| COUPON_DETAIL | 券模板ID | 优惠券详情 |
| WALLET_DETAIL | 本人持券ID | 我的券详情 |
| ORDER_DETAIL | 本人购券订单ID | 购券订单详情 |

前端按 destination 映射现有页面，使用卡片 ID，不从模型文字提取跳转参数。正文当纯文本展示，不执行 HTML。券码和二维码不会进入助手响应，仍通过原持券详情流程获取。

支持公开门店、当前可领购券、本人券包/购券订单及规则解释。不代领券、下单、支付、取消订单；这些动作仍在原页面确认。一次最多8张卡片，公开候选最多扫描2000条；partial=true 表示结果截断或还有更多，不能宣称全平台最低价。私有列表是最近记录，不支持任意商品名/时间/金额组合筛选。有位置的附近查询范围为10公里，区域文字按地址匹配。

degraded=true 表示模型阶段失败：意图识别失败时没有执行查询；回复组织失败时保留真实卡片。显示说明、卡片和重试入口，不把失败当无数据结论。

### 22.3 清除、异常和配置

`DELETE /app/ai/assistant/session?sessionId=服务端会话ID`，成功返回 R.ok。会话不存在、过期或不属于本人时业务 code=404；清除本地 ID，允许用户重新开始。401退出登录流程；其他非1000业务码展示message。请求参数无效沿用业务错误，不保证统一400。

会话当前在单进程内存，空闲30分钟失效，最多2000个，保留最近6轮。退出或切账号清空本地会话与卡片；重启后需重建，多实例须粘性路由或共享会话存储。

连接复用 AiProperties 的文本模型配置。当前代码通过可选 UserAssistantPolicy 检查独立开关/额度；未注入策略时启用且不限次，不能声称已有控制台限额。用户聊天与图片额度不是同一计数。以上为代码契约核对，不代表已完成部署或移动端真机验收。

## 23. 核销移动端 AI 聊天与只读数据接口

### 23.1 账号与能力

使用商家登录产生的有效 STORE 门店员工令牌，沿用 Authorization 和门店工作空间上下文；OWNER、普通 APP、运营账号不能代用。路由要求 bill:view；查券额外要求 coupon:view，验券预检额外要求 redeem:use。服务端再次校验有效岗位、唯一门店与本人/全店数据范围；参数不能扩大权限。

`POST /merchant/ai/assistant/chat`

```json
{"sessionId":null,"message":"今天我核销了几张？","couponId":null,"orderId":null,"code":null}
```

message 必填1～1000字；sessionId 首次省略或null，后续原样回传。couponId 为券模板ID，orderId 为消费单ID（不是购券订单），都是待后端校验的页面上下文。code 只通过独立字段提供，不能写入 message；不保存到会话，下次验券需重新传入。

```json
{
  "code":1000,"message":"success",
  "data":{
    "sessionId":"服务器返回的会话ID","message":"今天暂无成功核销。",
    "action":"STATISTICS",
    "conditions":{"period":"TODAY","startDate":null,"endDate":null,"operatorId":123,"couponId":null,"orderId":null,"keyword":null},
    "cards":{"successfulRedemptions":0,"failedAttempts":null,"knownConsumptionYuan":0,"unknownAmountGroups":0},
    "suggestions":["改查近七天","改查今天"],"degraded":false,"operation":"READ_ONLY"
  }
}
```

### 23.2 按 action 渲染

| action | cards形态与能力 |
|---|---|
| STATISTICS | 统计对象；成功核销数、已知消费金额、未知金额组数等 |
| RECORDS | list/total/partial对象；最近20条，不当作全量 |
| COUPONS | 券分页或详情的白名单字段；本店可见不等于已发布或能核销 |
| ORDER | 精简消费单卡片；需消费单ID，不支持按订单号搜索 |
| INSPECT | 权威验券结果白名单，或valid=false/reason；仅预检 |
| ASK / UNSUPPORTED | 空数组，展示回答与建议，不执行写操作 |

与用户助手不同，本接口 cards 不是固定数组，必须按 action 分支处理。operation 仅 READ_ONLY/NONE，不返回代核销、支付、撤销等写入成功。degraded=true 为查询结果保留但模型总结失败；意图识别失败返回503，允许重试。

日期枚举 TODAY/LAST_7_DAYS/LAST_30_DAYS/CUSTOM；自选日期 yyyy-MM-dd，上海自然日、结束日包含，最多366日且不能晚于今天。店员只查本人，有全店范围的岗位才可查全店或指定 operatorId。同账单金额去重，缺失/冲突金额计未知组；failedAttempts 始终null，不能显示为0次失败。knownConsumptionYuan 单位元，订单 Cents 字段单位分，不能将消费金额写成收入。

### 23.3 清除与独立查询接口

`DELETE /merchant/ai/assistant/session?sessionId=服务端会话ID`：成功R.ok；未知、过期或其他账号/门店/登录令牌会话返回409。当前会话单进程保存、空闲30分钟过期、最多2000个，后端重启失效。切账号/退出清空本地会话；409后清空会话ID并提示重新开始。

聊天页面通常只需 chat/session。下面5个已实现接口可供专用只读界面直接使用；响应均包在R.data中，原业务数据接口与聊天cards投影不同：

| 方法 | 完整路径 | JSON请求 | data |
|---|---|---|---|
| POST | /merchant/ai/assistant/statistics | {"period":"TODAY"}；可选startDate/endDate/operatorId | 同统计服务结果 |
| POST | /merchant/ai/assistant/coupons | {"keyword":"咖啡"} 或 {"couponId":123} | 原门店券分页（固定首20条）或详情；couponId优先 |
| POST | /merchant/ai/assistant/inspect | {"code":"扫码内容"} | 原权威验券预检结果，规则见第11章 |
| POST | /merchant/ai/assistant/order | {"orderId":123} | 原消费账单详情，见第12章 |
| POST | /merchant/ai/assistant/records | 无请求体 | 原核销记录首20条，见第13章 |

### 23.4 启用条件与错误

当前 MerchantChatPolicy 默认关闭；聊天需配置 `perkly.ai.merchant-chat.enabled=true` 且 `perkly.ai.merchant-chat.daily-limit` 为正整数，并配置可用文本模型连接。额度按账号、上海日期在单进程内存计数，包含失败尝试，重启清零；未接共享持久限额，不能当作严格生产计费。该策略在chat执行，不应把5个直接查询接口描述成模型聊天收费。

401登录失效；403身份/权限/范围不足；400非法参数；409会话失效；429额度耗尽；503未开通或模型异常。兼容现有业务错误message，不能只凭HTTP200判成功。手机不应通过调用写接口“补做”AI不支持的动作。

### AI 数据一致性补充（2026-11-10）

两个移动端请求字段不变。用户助手的本人订单/券包结果 note 保留当前状态条件下的数据库全量总数和本次展示条数，partial 为 true 时不能把 cards.length 当作总数。核销端统计使用汇总或 total，不使用当前页条数代替全量。门店 AI 客服检索到的有限卡片不能用于推断全部订单或券数量。未经核实不将差异解释为权限、缓存或同步问题。

新增 POST /merchant/reports/redemptions/query 和 GET /merchant/reports/redemptions/operators，普通bill:view权限，不依赖AI配置。支持汇总、补零趋势、历史券类型分布、人员统计、人员选项和统一搜索分页。协议及验收限制见 [报表说明](../docs/门店核销报表接口-20261110.md)。
