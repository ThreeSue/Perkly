## 用户移动端：推荐列表

`POST /app/recommendation/page`，携带现有 APP 登录 Authorization。顾客身份从登录态读取，**不接受 customerId 指定他人**。商家/门店移动端没有跨商家画像接口。

请求示例（字段可省略）：

```json
{"kind":"COUPON","page":1,"size":20,"keyword":"咖啡","categoryId":null,"merchantId":null,"storeId":null,"type":null,"maxPriceCents":2000,"latitude":null,"longitude":null,"radiusMeters":null,"sort":"PERSONALIZED"}
```

|字段|说明|
|---|---|
|kind|COUPON / STORE，默认 COUPON|
|page / size|默认 1 / 20；page≥1，size 1–100|
|keyword|可选，最多100字，按原公开查询匹配券名/商家名，门店查询同时匹配地址|
|categoryId|商家行业分类，不是 VIP/旗舰等门店类型|
|merchantId / storeId|可选正整数，限定商家/适用门店；STORE 时 storeId 精确限定门店|
|type|仅优惠券；FULL_REDUCTION / DISCOUNT / CASH / PACKAGE / EXPERIENCE / EXCHANGE|
|maxPriceCents|仅优惠券；非负整数，购券售价上限，单位分，0代表仅免费券；不是消费预算或人均价|
|latitude / longitude|两者同时提供，GCJ-02；范围分别 ±90 / ±180|
|radiusMeters|可选，0 < 值 ≤ 100000；需要定位，没有定位会报参数错误，不假称附近|
|sort|PERSONALIZED 默认；PRICE_ASC 仅券；DISTANCE 按距离。显式排序优先于画像偏好；无定位时返回 NO_LOCATION 并按稳定次序兜底|

响应仍用 `{code:1000,message:"success",data:...}` 包裹。下例是结构示意，不是当前数据库记录：

```json
{"code":1000,"message":"success","data":{"list":[],"total":0,"page":1,"size":20,"rankingDate":"2026-11-10","profileRevision":null,"locationMode":"NO_LOCATION"}}
```

- `list` 保留现有公开门店/优惠券卡片字段，券 `salePrice/minSpend/discountAmount/deductAmount/maxDiscount` 仍为**分**，不是元。新增 `recommendationReason` 为简短真实排序依据，不是喜欢概率。
- `total` 是本次全部合格候选总数，不是本页数量。接口会遍历全部公开候选，已下架/停业/售罄/过期/未开售/已达个人领购上限的券不会推荐；卡片仍需在领购时由原交易接口复核。
- `rankingDate` 为北京时间当天；`profileRevision` 是使用的画像版本，可为 null；`locationMode` 为 GCJ02 / NO_LOCATION。无画像走基础排序，不等待外部模型。
- 同一天、相同画像、相同候选与参数的排序稳定。次日探索权重变化；库存、上下架、画像更新会改变列表，客户端刷新时重置 page=1，并按 id 去重。不是冻结库存的游标快照。
- 首页门店和券推荐调用本接口；用户 AI 导购共用排序器，并继续遵守会话中的区域、免费/付费、价格和预算约束。“我的券”和订单保持原排序。
- 未开启画像任务时推荐仍可提供基础结果，profileRevision=null。打开任务后，首次/跨日推荐请求仅提交合并任务，不等待模型；模型失败保留旧画像并有限重试。
- 既有公开发现列表接口未强制改为个性化，前端需要主动切换首页推荐调用。不要将业务筛选页的用户明确排序强制替换为画像排序。

## 运营端接口

仅 PLATFORM 管理员或获得对应权限的运营账号使用；商家/门店身份即使猜中顾客 ID 也不能查看。

|方法|路径|权限|参数|
|---|---|---|---|
|GET|/admin/profile/info|profile:read|query customerId|
|POST|/admin/profile/refresh|profile:update|JSON `{customerId}`，提交异步分析，不是同步完成|
|POST|/admin/profile/preview|profile:read|query customerId；JSON 与用户推荐请求相同|
|POST|/admin/profile/correction|profile:update|JSON `{customerId,excludedLabels:["咖啡"]}`；只允许排除已有标签，空数组恢复|

info/refresh/correction 的 data 包含 customerId、revision、cutoff、updatedAt、state、errorCode、evidence、interpretation、modelVersion、promptVersion、excludedLabels。

- state：NOT_BUILT / PENDING / RUNNING / COMPLETED / FAILED。errorCode 非空时要提示本次更新未完成，不能清除已经显示的旧画像。刷新关闭或切换用户后停止轮询；管理端实现为待处理时每5秒刷新。
- evidence.statistics.windows 含 30/90/180 天：visits、freeClaims、paidPurchases、knownAmountVisits、unknownAmountVisits、consumptionCents、purchaseSpendCents、categories、priceBands、knownDiscountVisits、discountedVisits、discountCents。未知消费金额不补零、不计入价位样本。
- categories：categoryId、visits、knownAmountVisits、consumptionCents、lastVisit、meanGapDays、evidence。平均间隔按不同且时间精确的消费日计算，不足2个消费日返回 null。名称从 evidence.categoryNames 显示，勿把数据库ID当名称。
- sufficiency：NO_CONSUMPTION / LIMITED / SUPPORTED，是后端按样本量划分的可解释提示，**不是模型置信概率**。
- interpretation.tags 每项 label/contentKey/quote/factKeys，引用必须来自已读取业务事实，后端逐条校验；不能凭空添加收入、年龄等推断。
- 纠正标签保存在独立表，重新分析不会自动恢复已排除标签。它不修改原始消费事实、行业分类或原始模型历史版本。
- 金额为 long 分；时间保留时区信息或由项目时间序列化配置输出，客户端使用带时区方式解析。模型与提示词版本供追溯，不需要展示给移动端用户。

## 部署与测试边界

1. 备份后手动执行四张增量表 migration：profile_snapshot / profile_job / profile_history / profile_correction。没有自动导入开发库数据。
2. 配置 `perkly.profile.worker-enabled=true`；默认 false。沿用已有 `BAILIAN_API_KEY` 与 qwen3.8-flash。AI 控制台全局开关也须开启。此开关目前与已有 AI 控制台共用，未另造独立图片计费额度。
3. 重启后给需要的运营岗位授予 profile:read/profile:update，用户列表出现“用户画像”。商家岗位不授予跨商家画像。
4. 每15秒领取一个任务；同一顾客待处理任务合并，模型在短事务之外运行；最多3次，失败等待60/120秒再尝试，租约180秒。成功版本保存快照与历史，失败不覆盖旧快照。
5. 隔离库测试使用 `perkly_ai_regression_20261106`，六类输入每次创建后回滚。模型实测仅发送硬编码虚构样本，不使用真实顾客数据。

当前限制：按需跨日更新，未做定时扫描全部顾客；当前明确需求作为查询约束生效，未建设永久的用户偏好编辑档案。排序不凭不存在的门店人均价推断价格匹配，不用曝光/点击历史，不提供真实转化提升承诺。2.0再加入埋点反馈和大规模召回索引。
